# EI-WORLD-ADD-015 — добавление карты в мир

Проектирование 2026-09-17, база Ataman 14. Реализовано в версии 15.
Решение владельца: состав и координаты мира только через world-map-layouts.json,
без зависимости от map.txt и без регистрации игровых переходов.
Проверки и фактические границы: validation/ATAMAN_WORLD_JSON_15.md.
Ниже сохранён проектный сценарий; технические пункты отражают исходное исследование.

## Рекомендуемый пользовательский сценарий

1. Кнопка «Добавить карту в мир…» рядом с «Расставить карты».
2. Выбор существующей карты профиля либо MPR с диска. MOB подставляется
   по совпадающему имени, если найден; его можно выбрать явно или оставить
   пустым для карты, пока содержащей только рельеф.
3. Название, выбранный мир и размеры карты показаны в одном окне.
   Размеры читаются из MPR, а не вводятся вручную. Для первой карты можно
   создать мир редактора; она становится его опорой с координатами 0,0.
4. После проверки появляется полупрозрачный прямоугольник карты у курсора
   с размерами и координатами. ЛКМ размещает, Esc отменяет без записи.
   Привязка к границам соседних карт помогает состыковать рельеф.
   Пересечение показывается, но не запрещается: у карт бывают пустые края.
5. При подтверждении сохраняется состав мира и координаты; сцена карты
   загружается существующим фоновым механизмом. Камера остаётся на месте.
6. Карта доступна после перезапуска, перемещается через «Расставить карты»
   и открывается для редактирования обычным действием. «Убрать из мира»
   удаляет только членство в раскладке, сохраняя MPR/MOB.

## Данные и границы

- Сохранять состав мира в существующем world-map-layouts.json профиля,
  рядом с аддоном. Расширение требует новой версии схемы и чтения старой.
  Старое приложение должно отклонять новую схему, а не тихо терять поля.
- У записи карты собственный стабильный ID; имя файла и игровой zoneId
  не служат её единственной идентичностью. Для зарегистрированной игровой
  карты хранить необязательную ссылку на её zoneId.
- Отдельная сущность мира редактора с собственным ID и опорой; игровой allodId
  может быть ссылкой, но членство не зависит от наличия игровых переходов.
- Пути внутри профиля относительные; внешние файлы остаются внешними ссылками
  с понятным обозначением. Никакого скрытого копирования ресурсов.
- Проверять читаемость MPR, его размеры и нужные ресурсы, а MOB — если выбран.
  Один и тот же физический MPR не добавлять дважды в один мир: документы
  рельефа сейчас кэшируются по пути, независимые экземпляры потребуют иной модели.
- Запись атомарная с резервной копией перед миграцией. Проверять хеш исходного
  JSON перед заменой, чтобы второй редактор не затёр изменения первого.
- При недоступном файле сохранять запись и показать «Файл не найден» с выбором
  нового пути; не удалять карту из мира автоматически.
- Сброс автоматических координат игровых зон не должен удалять добавленные
  вручную карты. Удаление опорной карты требует выбора новой опоры без скачка
  мировых позиций оставшихся карт.

## Подтверждённые места изменений

- source/documents/world_map_layout_document.*: сейчас хранит только координаты
  игровых зон, schemaVersion=1; resetAllodLayout пересоздаёт аллод из map.txt.
  Нужны членство, миграция, add/remove и защита от внешнего изменения JSON.
- source/resources/neighbor_map_layout.cpp: требует игровую запись каталога,
  совпадение аллода и componentAnchorZoneId; новый состав мира должен независимо
  давать render placements для импортированных MPR.
- source/app/main_window.cpp: refreshMapTestContext связывает мир с m_mapTestEntry.
  Нужен отдельный контекст мира; нельзя подмешивать редакторские ID в игровой
  каталог, переходы, сценарии и Test Current Map.
- openMapPairWithCameraPolicy требует MOB. Для MPR без MOB нужен нормальный
  путь открытия рельефа с той же политикой несохранённых изменений и камеры.
- source/render/view.cpp: hardcoded maximumNeighbors=5. Список участников мира
  отделить от бюджета загрузки; только что добавленная/выбранная карта должна
  иметь приоритет и быть видимой. Не загружать весь большой мир без лимита.
- Существующие CPU workers, generation cancellation, GPU upload batches,
  spatial groups и shared-terrain protection должны обслуживать новые карты.

## Проверки реализации

- Старый JSON мигрирует без потери координат; добавление, удаление и повторное
  открытие сохраняют состав. Esc и ошибка чтения/записи не меняют JSON.
- Профили изолированы; перенос папки мода сохраняет относительные ссылки.
- Дубликат пути, пропавший файл, ошибка MOB и конфликт внешней записи объясняются.
- Новая карта появляется даже при пяти уже загруженных соседях; старый CPU-result
  после смены профиля не возвращает удалённую карту.
- Открытие добавленного MPR/MOB не получает чужие входы/скрипты; MPR без MOB
  открывается без ошибки о неполной игровой паре.
- Добавление/перемещение/удаление из мира не меняет MPR/MOB/texts.res.
- Ручная проверка: расположить карту, перезапустить, открыть двойным щелчком,
  переместить, убрать из мира; проверить камеру и неизменность файлов.

## Если нужна игровая локация

Это расширяет результат: отдельная явная операция регистрации zoneId,
аллода, MPR/MOB, миникарты и переходов через редактор каталога map.txt,
с резервированием texts.res и проверкой повторного чтения. Географическое
соседство само по себе не создаёт игровых переходов. До ответа владельца
этот объём не считать выбранным и игровые ресурсы не изменять.
