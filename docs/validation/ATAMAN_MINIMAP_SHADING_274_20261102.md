# Ataman274 — поправка владельца: нейтральное затенение рельефа (R2, 2026-11-02)

## Действующий результат и оставшееся ограничение

Первое исправление a0ed2ef1 было выполнено **по неверно выбранному основному
сценарию**: оно лечило побочную RGB-экстраполяцию рассветного света, а не ожидаемое
владельцем нейтральное усиление тёмных склонов. Первоначальный DONE не закрывал

`453aa880dec6351f117ebe164e8c33c668277627`, установленная273. AGENTS SHA256
`2a2f58ef34f63d6c5d67d165d0b809b046d0a519181119d22ea8fdd8781fe3b7` сверён,
договоры из предыдущего этапа актуальны. Без установки/push/старых сборок/
видимых окон/computer-use/экрана владельца/буфера/Base-карт/ProgramData locks.

Новый нейтральный relief-pass реализован и технически проверен. Ползунок меняет
затенение рельефа; static geometry имеет одинаковый свет в unlit/shaded. Цвет
белого света не зависит от viewport/погоды/региона; направление — из карты.
**Точный исходный красный вид владельца на доступных сохранённых настройках
zone1 не воспроизведён. Его причину по одному снимку нельзя объявить доказанной;
приёмка исходного случая остаётся открытой.** В частности, новая гипотеза о
прямом влиянии viewport-часов опровергнута кодом и побайтовой матрицей до правки.

- Специальный shader-mode3 доступен только capture. Terrain unlit/shaded —0/3;
 static models —3/3. Viewport по-прежнему использует свои0/1/2 без изменения

- a0ed2ef1 оставлен: при shade>1 общий коэффициент pow(Llit/Lraw,shade-1)
 усиливает нейтральное затухание. Оно не смешивает новый цвет, не даёт

## 100%: правильный эталон и предел точности

Реальный полдень прежнего full renderer всё ещё имел цветной ambient floor;
считать его RGB-байты нейтральным эталоном нельзя. Поэтому отдельно построен
**калибровочный белый полуденный эталон** на прежних production draw/shader
объектах, заново собранных из453aa880: только test environment-resolver задаёт
белое солнце и нейтральную полуденную яркость. Это явная тестовая калибровка,
не воспроизведение owner-настроек. См. tests/minimap_relief_reference_environment.cpp
и reference/ (23 PASS). Никакая такая замена не входит в поставляемый пакет.

При WS_TIME12 новый100% визуально совпадает с этим эталоном: отличаются **3 из
1048576 пикселей**, max channel delta10, mean absolute delta1.2398e-5. Эти точки
лежат у границ статических объектов; между независимыми прогонами этой же новой
программы набор различий менялся6→3. Причина этой микровариативности не доказана;
строгое побайтовое совпадение всего100%-кадра **не PASS**. Цвет/форма рельефного
затенения на сравнительном листе совпадают. noon-reference-comparison.png

## Подтверждённая причина и условия

На штатных текущих DejaVu zone1/basecam и простом холме273 ползунок0/50/100/150
красного не даёт. Оба прохода имеют одинаковые размеры, ориентацию и корректные
цветовые каналы; baked inputs — ARGB32_Premultiplied, grading нормализует их
в ARGB32. Несоответствие размеров, RGBA/BGRA и премультипликация не объясняют дефект.

На **той же частной zone1**, с единственным контролируемым изменением WS_TIME=4
в памяти, красный вид воспроизведён при128–150%, как с нейтральными цветами,
так и со штатными saturation110/brightness106. Эти изменения не сохранялись в MOB.
При0/50/100 ошибка экстраполяции отсутствует;100% уже содержит нормальный тёплый
цвет рассвета. Конкретная карта/все параметры исходного снимка владельца не были
доступны; совпадение его точного состояния не утверждается.

Первое неверное значение возникает в gradeMinimapImage, до hue/saturation/contrast/
brightness: `raw + (lit-raw)*shade` при shade>1 продолжает независимо уменьшать
RGB-каналы цветного освещения. Каналы проходят ноль в разное время. На150%
отрицательны R у2, G у12 и **B у439841 пикселя**. Синий затем обрезается до0,
усиливая красный вместо дополнительного затенения. Пример реального пикселя:
`(17,0): unlit [85.0, 84.0, 79.0], shaded [46.0, 33.0, 25.0], old150 [26.5, 7.5, -2.0]`. Это не ошибка слайдера или GL readback.

По истории исходников диапазон150 и эта экстраполяция добавлены upstream
`3b156c9729673f0d2c88b12393cb400151cce234` (0.3.0-alpha.24). Первая функция
minimap_bake.cpp побайтно одинакова в Ataman1 `e65e72e9`, закреплённой131
`5a81105903c4462a6694f2dd1aefcbdf5086404b` и HEAD273. В Ataman1 присутствуют
также оба unlit/shaded прохода. Дефект унаследован **уже Ataman1**;
связь с266–269/254 не подтверждается. Исторические сборки не запускались.

## Исправление

Только при shade>1 берётся цвет shaded100 и умножается на общий коэффициент
`pow(luma(shaded)/luma(unlit), shade-1)`. Это продолжает затухание яркости,
сохраняя цвет освещения; независимой RGB-экстраполяции и отрицательных каналов
больше нет. Для нулевой яркости unlit деление исключено. Чёрные shaded и альфа
сохраняются.0–100% оставлены в прежней ветке, последующие цветовые регуляторы
не менялись. Ограничение диапазона слайдера150 не сужено; clamp не используется
для маскировки причины.

Рендер, захват, световые таблицы и игровые данные не менялись. Сохраняется
естественный тёплый цвет рассвета на100%; новый красный сдвиг при повышении
интенсивности устранён.

## Неуспешные диагностические попытки и отдельная находка

Первый harness неправильно сравнивал default saturation110/brightness106 с
нейтральным shaded100; исправлена предпосылка теста, программа не менялась.
Первая простая карта использовала новый namespace без собственных текстур и
показывала серую заглушку. Итоговая синтетическая карта использует исходный
DejaVu namespace/атлас; before-simple/after-simple274 без missing terrain textures.

В общем многокарточном прогоне274 при переходе simple→zone1 произошёл crash
до рассветного capture и gradeMinimapImage: `0xc0000005`, `0x5f59a7`,
CLandscape::projectPositions, первая инструкция разыменования аргумента списка
узлов. Это штатный вызов reprojection из ensureTerrainAutoCatalogReady при
повторном открытии; состояние/причина порчи аргумента не установлены. Link map:
`build-source-274-minimap-shading/build-shading-check/shading.map`, crash:
`work/minimap-shading-274-20261102/diagnostics/crash.txt`, исходный протокол `after/stdout.txt`.
Этот прогон **не PASS**. Отдельная находка не исправлялась за счёт изменения
чужих renderer-файлов; требует самостоятельного исследования жизненного цикла
при переключении. Все заданные экспортные сценарии затем полностью проверены
в отдельных процессах с нормальным завершением. Ручная приёмка владельцем
остаётся отдельной; точное исходное состояние его снимка неизвестно.
