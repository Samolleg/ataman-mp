## Причина в коде

1. `source/render/view_world_terrain.cpp:1059–1081`: обработчик последовательно вызывает `CTerrainMixedEdge::resolve` для карт группы в том же UI-потоке. Снимок подтверждает именно этот путь установленной программы.
2. `source/documents/terrain_mixed_edge.cpp:291–337`: для очередной смешанной ячейки вызывается полный `CTerrainRecipeBaker::bake` и только после получения изображения выполняется `mixedEdgeSlot(recipeKey)`. Уже имеющийся recipe slot поэтому не предотвращает запекание. Внутренний recipe cache baker создаётся заново при каждом вызове, а вход здесь содержит только одну ячейку.
3. `source/documents/terrain_recipe_bake.cpp:17–22,120–153,164–200`: `pairOwnership` вызывает `seed(p.ids[a],p.ids[b],0)`, реализованный через выделение QByteArray и SHA256, из пиксельного цикла. Значение неизменно для данной пары материалов. На сложных стыках вызов выполняется для нескольких пар на пиксель. Живой стек попал непосредственно в этот SHA256.
4. Baker дополнительно заново проверяет и подготавливает исходные изображения на каждом одноячеечном вызове (`terrain_recipe_bake.cpp:538–610`). Вклад этого участка в общее время отдельно не измерялся.

Наблюдения доказывают неправильное размещение и повторение дорогой работы. По одному снимку не определяются точные доли затрат, причина общего объёма памяти и полная длительность успешного ремонта.

## Следующий шаг

Необходимое исправление: вычислять ключ/вариант/runtime type до растеризации и использовать готовые рецепты; готовить исходники и постоянную фазу каждой пары один раз; выполнять длительную транзакцию вне блокирующего обработчика с прогрессом и отменой, применяя итог атомарно и сохраняя Undo/Redo, native размеры, воду и анимации. Простая замена SHA на другой алгоритм изменила бы пиксели; выводить вычисление из пиксельного цикла следует с сохранением прежнего значения.
