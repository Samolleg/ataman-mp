### Красный результат и причина

Свежий git archive точной281 R1 и новая Release, не прежние исполняемые сборки.
На реальной копии DejaVu каталог имеет ровно одну запись gz10g для zone10.mpr.
Обычный openMapPair(zone10.mpr, zone10_work.mob, без zoneId) успешно загружает
скопированную структурно основную MOB, однако R1 оставляет зону пустой:
**0 входов**, travelZone пустой. Общая zone1.mpr + zone1_work.mob также теряет
зону и все входы. При unknown explicitId после неудачного поиска эффект тот же.
Красный результат получен до изменения production-функции.

Причина: continue при несовпадении MOB пропускает и точную MPR-запись,
и её добавление в nameMatches. 280 выбирала первую точную MPR-запись,
независимо от имени/пути MOB, вне строгого world.

### Исправление и зелёная проверка

перед fallback по имени. Найденный явный zoneId по-прежнему выигрывает до

### Другие случаи потери непустой зоны280 в той же функции

Помимо переименования файла, тот же mismatch возникает при копировании MOB
в другой каталог с прежним именем, при явно подобранной другой MOB, при
отсутствующем/ином mobPath в записи каталога и при нескольких загруженных MOB,
когда выбранный mapTestStagingMob() не совпадает ни с одним кандидатом MPR.
Это один класс по условию сравнения путей, а не отдельные ошибки парсера.
Он проявляется также при непустом, но **не найденном** явном zoneId — этот
вариант дополнительно подтверждён красным/зелёным тестом выше.

Исчерпывающая граница найденной потери: вывод по каталогу разрешён, явная
идентичность не найдена, существует точное совпадение MPR, helper возвращает
MOB с несовпадающим путём для всех MPR-кандидатов, и оставшиеся nameMatches
не дают единственную альтернативу. R1 могла вернуть пустую зону там, где280
уже выбрала первую MPR-запись. R2 восстанавливает весь этот класс вне world.
Без helper-MOB не-world281 и раньше брала первую MPR; без точного MPR поиск
по имени не менялся. Подавление inference для явно unmapped collection,
найденный явный zoneId и строгий world не добавляют иных случаев такой потери.
