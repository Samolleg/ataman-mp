# Аудит Ataman 243: надёжность, производительность и проверки

Дата: 30.10.2026. Задача: **EI-AUDIT-243-20261030**.
База: `main`, `a6b2c2f650fb37ff12be368159415bfad19f7c25`, VERSION **243**.

Найдены три проблемы P1, подтверждённые изолированными примерами: выход за
границы памяти при построении FIG, неограниченное выделение памяти из заголовка

P1 здесь означает аварийное завершение, исчерпание памяти или нарушение защиты
от конкурирующей записи. P2 — существенную масштабируемую затрату либо пробел
в регрессионных проверках. Это приоритеты исправления, не оценка частоты сбоев
на обычных игровых ресурсах.

## A243-01 — P1: повреждённый FIG приводит к обращению вне массива

**Подтверждено на текущем Release-коде.**

Код: `source/render/figure.cpp:172`, `:190–231`;
`source/resources/resourcemanager.cpp:496–500`, `:615–623`.

`CFigure::readData()` читает счётчики и массивы, отмечает неверные индексы через
`m_completeCaptureGeometry=false`, но всё равно возвращает `true`. В обычном
пути построения модели `generateTriangles()` обращается к `m_aVertComp[ind]`
до проверки границ. Проверка отдельных normal/vertex/UV внутри
`decodeFigureVertexComponent()` находится уже после этого обращения.
`prepareStaticAssembly()` также вызывает `getVertexData()` без отказа по флагу.

**Воспроизведение:** синтетический FIG8 длиной 828 байт; один блок вершин,
один блок нормалей, одна UV, три индекса и одна vertex component. Контрольные
индексы `0,0,0` дают одну часть/три вершины. При индексах
`65535,65535,65535` чтение возвращает успех, `completeCaptureGeometry()`
возвращает false, а публичный `getVertexData(..., upload=false)` завершается
с **0xC0000005**. Никакого OpenGL-контекста для этой аварии не требуется.
Отдельный обрезанный до 40 байт FIG также получает `readData=1` при
`QDataStream::ReadPastEnd`.

Счётчики FIG дополнительно не ограничены доступной длиной входа перед
`readVertices()`/`fill()`. Исчерпание памяти этой отдельной веткой не запускалось;
отсутствие проверки видно в коде, но отдельный crash для неё не заявляется.

**Исправление:** проверять счётчики/расчётные длины до выделения, завершать
чтение отказом при ошибке потока, проверять все индексы перед построением
геометрии. Сохранить поддержку пустых transform-only корней. Регресс:
корректная модель, пустой корень с детьми, обрезанный файл, неверный индекс и
завышенные счётчики; отказ не должен закрывать документ.

Доказательства: `figure_probe.cpp`, `figure_probe.pro`,
`figure-probe-results.json`, `figure_probe-{valid,truncated,invalid-parse,invalid-draw}.log`
в каталоге аудита.

## A243-02 — P1: число mip-уровней MMP не ограничено до выделения памяти

**Подтверждено синтетическим входом с ограничением памяти процесса.**

Код: `source/resources/mmp_inspector.cpp:58`, `:100–122`.
Достижимые вызовы: `source/ui/resource_browser.cpp:255`,
`source/app/main_window.cpp:5204`, `source/ui/map_table_editor_dialog.cpp:965`,
`source/ui/travel_global_map.cpp:108`.

В DXT-ветке `mipValue` из файла управляет циклом. Каждая итерация добавляет
`QSize` в `authoredMipSizes`. После достижения 1×1 цикл продолжает добавлять
уровни. Проверка суммарной длины относительно входа выполняется только после
всего цикла. Поэтому короткий файл может потребовать гигабайты памяти ещё до
диагностики обрезанного payload.

**Воспроизведение:** корректный контроль 1×1 DXT1 — 84 байта, один уровень,
успешный результат. Ошибочный файл — только 76-байтный заголовок, те же размеры
и `mipValue=0xffffffff`. В собственной Windows Job с лимитом private memory
128 МиБ получен `std::bad_alloc` через 45 мс, пик commit процесса
104 075 264 байта. Исключение перехвачено только диагностическим примером.
Этот запуск не доводил компьютер до глобального дефицита памяти.

**Исправление:** до цикла ограничить число уровней допустимой цепочкой от
размеров изображения и доступными байтами, проверять длины по мере чтения.
Отдельно обработать отказ создания `QImage`. Регресс — все поддержанные
форматы, неполные/избыточные цепочки, UINT_MAX и корректная последняя 1×1.

Доказательства: `mmp_probe.cpp`, `mmp_probe.pro`,
`mmp-probe-{valid,invalid}.log`, `supplementary-results.json`.

## A243-03 — P1: экспорт миникарты обходит блокировку общего RES

**Обход блокировки подтверждён; реальная потеря чужих данных не инсценировалась.**

Код: `source/documents/res_texture_export.cpp:40–193`;
вызов из фоновой операции: `source/ui/minimap_export_dialog.cpp:758–761`.
Договорённый lock: `source/core/process_edit_lock.h:18–29`;
пример защищённого пути: `source/documents/res_save_coordinator.cpp:63–72`.

`exportMmpToRes()` читает весь архив, строит новый, делает backup и заменяет
его через `QSaveFile`. В этом пути нет `CProcessEditLock` для общего ресурса
и `CFileWriteActivity`. Сравнение с исходным RES сделано до резервирования,
а не непосредственно перед коммитом; для изначально отсутствовавшего файла
повторной проверки отсутствия нет.

**Воспроизведение:** для собственного `textures.res` удерживается именно
`<canonical-path>.mapper-resource.lock`. Контрольный
`CProcessEditLock::acquire(..., map=false)` ожидаемо отказывает. При всё ещё
удерживаемом lock `exportMmpToRes()` успешно добавляет валидную текстуру 64×64
и изменяет архив: `resourceLockHeld=1 guardedAcquire=0 exportSuccess=1 changed=1`.

Таким образом, экспорт может конкурировать с защищённой публикацией другого
маппера, работающего с другой картой и общим RES. Возможное следствие — замена
чужого обновления кандидатом, построенным из старого состояния. Наличие
backup и атомарной замены защищает от частично записанного файла, но не
устраняет этот конфликт версий.

**Исправление:** направить экспорт через общий координатор сохранения с
resource lease на весь цикл, учётом активной записи и проверкой исходного
состояния непосредственно перед заменой. Сохранить точную проверку остальных
members, backup и fresh reopen. Регресс — занятый lock, два писателя,
внешняя замена во время подготовки и появление ранее отсутствовавшего файла.

Доказательства: `res_probe.cpp`, `res_probe.pro`, `res-probe-lock.log`.

## A243-04 — P2: экспорт небольшой текстуры удерживает много полных копий RES

**Подтверждено измерением.**

Код: `source/documents/res_texture_export.cpp:59–172`;
`source/documents/res_archive_document.cpp:126–127`.

В одной области живут original/baseline, candidate, reopenedBytes/reopened,
fresh, published/publishedArchive. Разбор RES дополнительно материализует
payload каждого member. Большая неизменяемая часть архива тем самым
многократно удерживается в памяти ради добавления маленькой миникарты.

Каждый замер — отдельный процесс, один неизменяемый синтетический member,
новая валидная DXT1-текстура 64×64. Время относится к вызову экспорта;
`PeakPagefileUsage` — пиковый commit процесса, включая его служебные затраты,
а не RSS/VRAM. Источник только что создан, то есть файловый кэш тёплый.

| Полезная нагрузка исходного RES | Экспорт | Пик commit процесса |
| --- | ---: | ---: |
| 16 МиБ | 398 мс | 153 645 056 байт / 146,5 МиБ |
| 64 МиБ | 1 646 мс | 607 510 528 байт / 579,4 МиБ |

Это одиночные контрольные измерения, не p95 и не прогноз времени для игровых
архивов. Они уже показывают масштаб проблемы памяти. Задержка не равна
доказанной блокировке GUI: этот экспорт вынесен в worker с анимированным диалогом.

**Исправление:** использовать имеющийся индексированный/потоковый путь RES
либо ограничить lifetime полных буферов и отказаться от повторного
материализования неизменяемых members. Проверки сохранности/гонок/backup и
reopen должны сохраниться. На повторном замере проверять peak commit и
побайтовую сохранность большого непричастного member.

Доказательства: `res-probe-{16mib,64mib}.log`, `res-probe-results.json`.

## A243-06 — P2: MCP revision синхронно перечитывает содержимое всех документов

**Полный обход подтверждён кодом; величина пользовательской паузы не измерена.**

Код: `source/app/ai_agent_edit.cpp:420–451`;
синхронная диспетчеризация: `source/app/ai_agent_server.cpp:315`, `:328`, `:332`.

Каждый расчёт revision заново хеширует исходные байты MPR, перебирает SEC и
виртуальные поля материалов, затем повторяет это для сохранённых документов
world terrain session и обходит объекты всех MOB. Есть и чтение layout JSON
с диска. Вызов выполняется в GUI-потоке из локального сервера; повторные
`get_revision` на неизменном состоянии не используют готовый digest.

Затрата растёт с объёмом удерживаемого мира, а не только с размером правки.
Это конкретный кандидат для профилирования больших multizone-сценариев;
ему не приписываются наблюдавшиеся когда-либо паузы маппера без замера.

**Следующий шаг:** замерить duration `get_revision` и задержку GUI-таймера на
одной/нескольких крупных картах, cold/warm и после правки. Затем рассмотреть
generation-based инвалидирование с переиспользованием неизменных digest;
точный отказ от устаревшего preview и обнаружение внешних изменений сохранить.

## Что не перенесено из старых аудитов и что осталось измерить

В текущем коде общая кисть уже передаёт previousTerrain, сравнивает payload
секторов и публикует только изменённые. `previewTerrainAtlasIfChanged()`
сравнивает разделяемые QImage и использует частичную загрузку.
`findExactArchive()` имеет bounded digest cache с Windows file ID/ChangeTime.
Журнал сессии ограничен 4 000 сообщениями. Поэтому старые тезисы о безусловной
полной публикации на каждом штампе, отсутствии proof cache или бесконечном
росте истории сообщений не объявляются текущими дефектами.

Не измерялись FPS/p95 реальной большой карты, press-to-present кисти,
холодное открытие игрового профиля, top-down экспорт полной сцены и игровые
переходы. Такие результаты требуют отдельного контролируемого прогона на
зафиксированной карте/камере/профиле; синтетические цифры выше их не заменяют.
Не запускались внешнее запекание Nav64 и специальные 18 сценариев с
непереданными fixtures. Не выполнялись полная Release-передача и установка.
