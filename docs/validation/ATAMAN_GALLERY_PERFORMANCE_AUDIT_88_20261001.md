## Подтверждённые причины

### G1. Полный список текстур заново строится в потоке интерфейса

`source/ui/model_gallery.cpp:211`, `CModelGallery::selectionChanged()`:
`clear()` и тысячи отдельных `addItem()` работают на модели, уже подключённой к editable QComboBox и QCompleter. QSignalBlocker блокирует сигналы самого combo, но не обновления модели/автодополнения.

Неизменённый класс, 7165 текстур, три повтора: конструктор1028.98–1436.39 мс, выбор следующей плитки1078.44–1527.40 мс. При100 текстурах выбор0.48 мс, при1000 —19.08–22.77 мс. Рост связан с числом элементов списка.

Окончательное инструментирование с настоящим порядком ресурсов: конструктор1108.06–1159.75 мс, выбор1043.12–1146.83 мс. Почти всё время находится в добавлении строк; получение подходящих текстур занимает примерно1 мс, очистка меньше1 мс. Первое неверное состояние — заполнение тысяч строк при подключённом автодополнении, до возврата из обработчика выбора.

Контроль без QCompleter ускоряет этот участок, но сохраняет ощутимые затраты подключённого списка. Отдельный контроль подготовки7168 строк вне подключённого combo, затем подключения целиком: подготовка1.87–2.66 мс, подключение0.13–0.97 мс; QCompleter сохранён. Это доказательство направления оптимизации, **не готовое исправление и не проверка всех функций такого исправления**.

При открытии `filter()` выбирает первую модель и вызывает этот обработчик. Затем оба вызывающих окна делают `setCurrentModel()` для исходного объекта и при другом текущем элементе запускают его ещё раз (`tablemanager.cpp:2894`, `createobjectform.cpp:737`). Поиск по каждому введённому символу, смена раздела/острова и `refreshCatalog()` снова вызывают `filter()`/полное заполнение. Поэтому секундная задержка умножается на число этих действий.

### G2. При просмотре готовых плиток повторно вычисляются подходящие текстуры

`model_gallery.cpp:178,280,296`: для каждой видимой плитки сначала вызывается `textureForModel()`, даже если изображение уже есть в кэше. `TechnicalModelCatalog::textureChoices()` (`technical_model_catalog.cpp:172`) линейно ищет связанные текстуры среди всего списка доступных. При отсутствии связи `TechnicalTextureCatalog::exactChoices()` (`technical_texture_catalog.cpp:188`) заново строит индекс доступных имён и обходит сохранённые результаты сканирования. Это работа с памятью/JSON, **не повторное чтение всех MOB-файлов**.

12 готовых плиток,50 проходов, без новых задач провайдера:

| Контроль | Время50 проходов | Сигналов dataChanged |
| --- | ---: | ---: |
| Исходное поведение | 382.38 мс | 600 |
| Только не присваивать готовую иконку повторно | 378.52 мс | 0 |
| Кэшировать результат выбора текстуры для неизменного каталога | 4.81 мс | 600 |

Следовательно, основной измеренный расход здесь — повторный поиск текстур:7.65 мс за проход против0.096 мс в диагностическом контроле. Повторные `setIcon()` вызывают лишние уведомления, но отключение только этих вызовов не устраняет основную задержку. Нельзя выдавать удаление setIcon за полное решение прокрутки.

### G3. Миниатюры последовательно загружаются с паузами; кэш ограничен одним окном

`model_gallery.cpp:169,280,296,307`, `model_gallery.h:65`:

- одновременно выполняется одна задача;
- следующая запускается через таймер40 мс после завершения предыдущей;
- кэш вмещает128 изображений и принадлежит конкретному диалогу;
- новый диалог создаёт новый провайдер и заново индексирует ресурсы;
- сцены/декодированные текстуры провайдер не сохраняет для повторного использования.

Даже с провайдером, мгновенно возвращающим простую картинку, первые12 плиток заполняются за719.41 мс. Кэширование выбора текстур уменьшает CPU-нагрузку, но первый экран всё равно занимает700.13 мс: остаются последовательная очередь и паузы. При возврате к вытесненным плиткам и при повторном открытии картинки требуется строить вновь; величина этого повторного пользовательского ожидания отдельно не измерялась.

Полный проход по497 реальным моделям с первым подходящим назначением текстуры: медиана4.179 мс, p95=12.978 мс, максимум112.789 мс; суммарное время провайдера3899.28 мс. Это прямые вызовы провайдера, **не время открытия всей витрины**: нормальный интерфейс заказывает лишь видимые плитки.

Для сложных персонажей `unhuli`, `unhufe`, `unhuzf`, `unorma` основное время занимает сборка сцены `.mod/.bon` с сотнями частей (751–812). Например, в предварительном инструментированном проходе у `unhufe`:131.72 мс сцена,2.93 мс текстура,3.37 мс программный рендер. Окончательный проход даёт меньшие абсолютные времена, сохраняя тот же доминирующий участок. Графический контекст/видеокарта не установлены причиной: эти картинки строятся программно в worker-потоке.

У простых проверенных объектов `nafltr23`, `stbr7`, `nast7` сцена занимает около1 мс, декодирование1024×1024 текстуры около9–10 мс, рендер меньше1 мс. Первое индексирование78 RES около28 мс. Линейный `CResourceCatalog::providers()` и повторное открытие RES присутствуют, но их отдельное устранение не доказано как главное решение секундного зависания интерфейса.

## MOB, JSON и дополнительные находки

Чтение текущего JSON — примерно1 мс, восстановление его scanCache —1.8–2.4 мс, перечисление213 MOB и проверка метаданных —4.3–4.9 мс. В актуальном кэше осталось **одно** задание. Утверждение «при каждом выборе пересчитываются все объекты всех MOB» текущие измерения не подтверждают.

Условный риск существует: обе формы запускают `scanNextFile()` через QTimer с интервалом0 в GUI-потоке. Если кэш отсутствует/устарел, чтение файлов блокирует обработку ввода отдельными порциями. В контрольном каталоге без restore ожидаются213 заданий; первые пять чтений занимали4.20–16.88 мс. Полное сканирование213 файлов не выполнялось, эти пять значений нельзя выдавать за время всего сканирования.

В панели свойств `openModelGallery()` копирует `m_textureScan` и сканирует локальную копию, не записывая её обратно. Он перечитывает JSON, но не восстанавливает scanCache из этой новой копии каталога. Внешний `setNewData()` восстанавливает кэш по токену источника. Следует проверить согласованность этих двух путей при обновлениях/отмене; повторное полное сканирование при каждом открытии **не воспроизведено**, считать его гипотезой.

JSON.save также вызывается перед открытием и после принятия. Если сериализация идентична исходной, запись пропускается; текущий замер не позволяет назвать эту операцию главным тормозом.

В отдельном полном проходе провайдер вернул пустое изображение для3 моделей: `nawa1`, `nawa2`, `unmoog`. Это отдельная находка G6; причина/нормальность специальных ресурсов не установлена. Не трактовать её как повреждение пользовательских карт и не ремонтировать данные.

## Почему предыдущие проверки пропустили проблему

`source/app/model_gallery_check.cpp` проверяет252 синтетические модели, **две** текстуры stone/wood и мгновенный mock-провайдер. Он подтверждает функции поиска/категорий/привязок и ограничение загрузки видимыми плитками, но не нагрузку7165 текстур, стоимость настоящих сцен, повторное открытие и плавность прокрутки.

Правка88 оптимизировала `CComboDynItem` панели свойств. Витрина использует собственный обычный QComboBox с отдельным циклом заполнения. Поэтому прежний быстрый замер выделения объекта не покрывал этот путь. В текущем workflow.log нет отдельных измерителей витрины; по нему нельзя распределить длительность пользовательских кликов между найденными стадиями.
