## Изменения

Диалог показывает открытие источников, индексацию, сопоставление слотов, восстановление переходов и подготовку публикации, счётчики N/M, общий монотонный процент и прошедшее время. Веса этапов: 0–5–35–55–90–100. Процент отражает объём этапов, а не долю общего времени. После 3 секунд и 8 обработанных единиц появляется приблизительная оценка до конца текущего однородного этапа. Общее оставшееся время не выдумывается из этих весов.

Рабочий поток обновляет защищённый mutex снимок; GUI считывает его каждые 100 мс. Обработчик Qt событий принимает пользовательский ввод. Расчёт MPR, разбор RES, оценка объёма и обход карт до подтверждения также перенесены в фон. Отмена кнопкой, Escape и закрытием окна запрашивает кооперативную остановку; поток не уничтожается принудительно. После остановки выводится «Подготовка отменена. RES и MPR не изменены.». После подтверждения «Да» прежняя публикация/backup/rollback остаётся неотменяемой; добавлена проверка полного SHA RES относительно подготовки.

Индекс HD-источников сохраняется в стандартном `cache/terrain-hd-index` рядом с EXE. Ключ: упорядоченные абсолютные пути, полный потоковый SHA256 каждого RES, размер и mtime. Один атомарно заменяемый файл на набор путей; изменение источников инвалидирует содержимое без накопления файла для каждого старого RES. Контейнер защищён checksum и схемой; повреждение приводит к построению заново. Кэш содержит тот же порядок источников, pixel/native indices, дескрипторы, provenance и калибровку. Кэш сохраняется только после успешно завершённой подготовки (в UI после «Да» или успешного no-op); отмена подготовки не записывает даже кэш. Для определения каталога используется чистый helper без фоновой очистки чужих старых visual caches.

Дополнительно ограниченные кэши по 32 МиБ повторно используют точные результаты BC1 round-trip при индексации и декодированные входы рецептов. Порядок кандидатов, формулы, калибровка и упаковка сохранены.

Долгая работа связана с повторной декомпрессией/сжатием, вычислением SHA/поворотов/дескрипторов каждого источника и поиском свидетелей переходов. Пик памяти объясняется одновременно удерживаемыми исходным и опубликованным RES-документами, каждый из которых хранит исходные байты и отдельные payloads, плюс кандидат очистки и его проверка. Старый документ теперь освобождается перед разбором нового. Во время ожидания подтверждения полные RES не удерживаются; после «Да» baseline перечитывается с проверкой SHA.
