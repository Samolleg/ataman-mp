## Прослеженный путь

1. `CView::deleteSelectedNodes()` (`source/render/view.cpp:24887`) собирает targets, сохраняет проверку script references и для нескольких целей открывает обычный `QUndoStack::beginMacro`. Это объединяет историю, но не откладывает выполнение redo каждого push.
2. Для каждого обычного объекта создаётся и немедленно исполняется `CDeleteNodeCommand`. Его `redo()` (`source/core/undo.cpp:84`) вызывает `CMob::deleteNode`, сигнал удаления и `CView::setDurty`.
3. `CMob::deleteNode(CNode*)` (`source/mob/mob.cpp:1856`) после каждого объекта заново собирает полный список логических узлов через `logicNodesUpdate`.
4. Сигнал приходит непосредственно в `CTreeView::onNodeDelete()` (`source/layout_components/tree_view.cpp:664`). ID игнорируется, запускается полный `CView::collectObjectTreeData()` (`source/render/view.cpp:21854`) с обходом объектов и пересборкой данных дерева, в логическом режиме также поведения/патрулей/точек взгляда.
5. `CView::setDurty()` (`source/render/view.cpp:26166`) без активного object-edit batch каждый раз вызывает `CMob::refreshDirtyFromProjection()` (`source/mob/mob.cpp:1755`). Он выполняет `serializeMob(currentProjection, false)` всего MOB и сравнение с clean projection/assembly projection; затем испускается mobStateChanged с обновлением панели.
6. Путь удаления использует обычный beginMacro, а не `CObjectEditBatchCommand`, добавленный184 для transform. Поэтому для N удалений полная проекция MOB и полное обновление дерева выполняются N раз. Обычный Undo/Redo макроса тоже повторяет эти действия для каждого дочернего удаления: undo вызывает restore, addNodeToTree и setDurty; addNodeToTree также вызывает collectObjectTreeData.

Подтверждены многосекундная серия удаления в184 и повторные полные операции в её исполняемом пути. Основной найденный источник лишней работы — отсутствие пакетного удаления. Отдельная доля дерева, сериализации, logicNodesUpdate и синхронных подписчиков в этих секундах не измерена; для её разделения нужен адресный таймер/профиль либо сравнительный native-прогон. Журнал не содержит таких таймеров. Полная причина одиночной задержки до первой Delete-записи этим анализом не установлена.
