## Полученный результат и причина остановки

Подготовлены общий cross-namespace индекс HD-источников, точное восстановление
части старых Modern-рецептов, сборка страниц с переносом оригинальных BC1-блоков,
кандидат MPR/profile/semantic migration и подключения UI/пакетной команды.
Это незавершённая реализация, не работающий подтверждённый релиз.

Команда UI: **Ландшафт → Дополнительно → Пересобрать атлас карты в HD…**,
objectName `terrainHdRepublish`. Пакетная точка входа:
`--terrain-hd-republish-check <fixture.json>`, JSON содержит `sources`, `archive`,
`maps`, `receipt`; `mode: "build"` и новый `output` запрашивают отдельные кандидаты.
Этот build-режим пишет только новую выходную папку, а не исходные карты.
UI-публикация предполагает существующие staged/backup/atomic coordinators.
**Её end-to-end корректность ещё не доказана.**

Первая функциональная проверка публикации читала собственную копию
`build-tests-138-hdrepublish/maps/basegipat.mpr` и разрешённые HDPack для чтения.
Она завершилась exit **2**:

```text
ERROR mpr.isolated_namespace_input: A loaded MPR, output buffer, and portable ASCII namespace are required
PASS: clipboard isolation backend=in-memory nativeAttempts=0 hookedImports=14
```

Причина прослежена по коду: `prepareTerrainHdPublication` передаёт
`content.result()` (32 бинарных байта) в `contentResourceIdentity`, тогда как
эта функция использует первые 12 байт как готовый текстовый суффикс.
В namespace попадают не-ASCII символы; `applyIsolatedNamespaceTransaction`
закономерно отказывает. Следующий необходимый шаг — корректно представить SHA
в текстовом виде, проверить portable namespace и добавить синтетический тест
**всего prepare/publication пути**, затем возобновить gates. Исправление после
FAIL здесь не выполнено: соблюдено поручение STOP на провале проверки.

MPR/RES кандидаты не записаны: создана только пустая папка
`smoke-candidate/basegipat/`, файлов в ней **0**. Receipt: `smoke.json`
(exit 2, 26.609 s, peakWorkingSet 373526528 bytes), полный вывод `smoke.out`.
Runner по ошибке назвал конфигурацию и process receipt одинаково `smoke.json`;
после завершения receipt заменил конфигурацию. Конфигурация воспроизводится
из `checks.py`, режим `smoke`; её имена при продолжении нужно разделить.
Эта ошибка учёта не вызвала production-отказ namespace.

## Точное сопоставление и неполные сведения о рецептах

Одно имя карты не задаёт происхождение её атласа. Например, сохранённый BaseGipat
содержит источники Zone3Obr, Zone9, Zone6_2; Zone11 ссылается на промежуточный
опубликованный namespace. Индекс охватывает stock namespaces HDPack Dejavu и,
как fallback при отсутствии HD-страницы, JamaisVu135; Base не является источником
для перепубликации своих карт.

Сравниваются точные RGBA hashes нативного 128 px mip восстановленного источника
и детерминированных BC1 publication generations 0…3. Это не perceptual matching.
При одинаковом 128 px результате разные HD-пиксели дают отказ
`ambiguous-HD-collision`; aliases/sourcePixelSha256 используются как provenance.
Надёжность этого пути ещё требует отрицательных тестов повреждённого provenance,
цепочек промежуточных namespaces и разных HD-источников с одинаковым SD mip.

Для Modern перебираются сохранённые signature/route owner, варианты production
масок и несколько наборов uniform-источников. Принимается только рецепт, который
после штатного BC1 encoding воспроизводит **все** прежние 128 px пиксели.
Разные HD-результаты одного SD witness не выбираются произвольно. Полное
восстановление всех legacy-рецептов не доказано. Устаревший mixed-edge хранит
хеш рецепта, но не brush bank; этот путь **пока не реализован**. В данном корпусе
у всех 14 активных опубликованных профилей mixedEdgeRecipes отсутствуют.
Нельзя на этом основании объявить поддержку mixed-edge успешной.

MMP задаёт один размер для всей страницы из 64 слотов. Вопрос владельцу о
частичном HD внутри такой страницы остался без ответа. В текущем черновике
использован консервативный вариант: вся страница остаётся побайтно 128 px,
если хотя бы один слот не восстановлен. Даже доказанные HD-слоты такой страницы
блокируются соседями. Это **не полное выполнение требования повысить каждый
доступный слот**. Возможное альтернативное решение — явно согласованный
nearest-neighbor перенос SD в 256 px ячейку без новой детализации; не считать
такой слот восстановленным HD.

Переносятся оригинальные BC1-блоки mip, где блок принадлежит одному слоту
(tile size ≥4). Самые малые mip разделяют один блок между несколькими слотами
и должны быть собраны из целой новой страницы. Это ограничение формата;
невозможно одновременно сохранить чужой shared block каждого исходного namespace.

## Память и бюджет

(около356.2 MiB), 26.609 s. Это индекс/подготовка, **не открытие карты**, не GPU/VRAM

Раскладка обязана сохранить исходные page/slot counts. Максимум корпуса —
Zone9,1600 slots/25 pages. Проекция полного256 набора: приблизительно66.667 MiB

Она ниже синтетического compressed workload8192×256 из
[исследования бюджета](ATAMAN_TERRAIN_MEMORY_SYNTHETIC_20261010.md), где новый
сжатый путь дал24/24 PASS. **Это проекция, не игровой замер и не новый PASS138.**
RGBA/assembly рекомендации1024×256 также нельзя автоматически заменить этим
compressed результатом. Реальные смешанные budgets нужно считать после сборки
кандидатов для каждой карты.
