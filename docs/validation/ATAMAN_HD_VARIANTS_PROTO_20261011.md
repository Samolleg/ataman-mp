# EI-HD-VARIANTS-PROTO — HD Stone / Desert и банк из шести вариантов

Дата: 2026-10-11. Исследование и автономный прототип, без версии, коммита,
сборки, установки и изменений программы. Поручение владельца выполнено на
приватном снимке; художественно пригодными все результаты не объявляются.

## Результат

**Stone / Desert класса 3 использует тот же рисунок, что класс 2.** Для
восстановления HD следует переиспользовать `bz16h:463` HD256 с отдельной
семантической идентичностью класса 3. Генерация первого HD не нужна.

Подготовлены четыре банка по шесть изображений: Grass / Tundra, Ground / Brown,
Ground / Stony gray и Stone / Desert класса 3. Всего 16 новых quilted-интерьеров,
7 существующих HD в своих материалах и один HD, переиспользованный для класса 3.
В каждом банке шесть изображений различны даже с учётом всех восьми симметрий D4.
Это доказательство различия пикселей, а не шести независимо нарисованных мотивов.

Кромка новых вариантов точно равна кромке назначенного исходного варианта,
включая повороты и полосу вокруг видимой UV-границы. **Новых разрывов относительно
этого исходника на базовом уровне нет. Уже существующие швы и орнаментальная
сетка остаются.** Особенно заметны исходные узлы тундры; вариант 6 серого
каменистого грунта имеет неприемлемую искусственную пестроту.

Полный исходный stock-банк: **96** неводных комбинаций с подтверждёнными
статическими opaque-источниками; **90** нуждаются в пополнении, **386** недостающих
семантических позиций. Одну закрывает переиспользование Stone / Desert;
остаётся **385 генераций**. BC1 256 со всеми mip: **16,088 МиБ** на 386 позиций,
либо **16,047 МиБ** на 385 новых изображений без отдельной копии reused HD.
Если потребовать шесть вариантов отдельно для каждого физического класса MP
внутри семантической группы, оценка повышается до **398 позиций / 16,588 МиБ**;
это отдельный, более строгий охват, описанный ниже.

|---|---:|---:|---:|---:|---:|
| zone18:463 / zone19:44 | 8,650 | 11,607 | 26,836 | 0,9622 | 0,8569 |
| zone19:43 / :45 | 8,816 | 11,760 | 26,723 | 0,9612 | 0,8549 |

У неверных поворотов RMSE 28,31…28,75 и корреляция яркости 0,074…0,103.
Между двумя SD-версиями: MAE **2,937**, RMSE **5,480**, PSNR **33,355 dB**,
Pearson яркости **0,9740**. У zone19:44 и zone18:463 MAE/RMSE **0**, SHA совпадает.
Просмотр PNG подтверждает одинаковое расположение больших трещин, наклонной
центральной гряды и симметричных угловых мотивов. Отличается обработка мелких
деталей; равенство downscale-HD исходному SD не заявляется.

Таким образом, это один рисунок в двух SD-обработках, а не два самостоятельных
мотива класса 3. Решение: источник pixels `bz16h:463`, semantic key
`Stone / Desert, reviewedClass=3, layer=land`, physical source class **2**.
Запрещено выводить физический класс из цифры 3 в имени семантической группы.
Для воспроизведения исходных клеток MP/SEC не переклассифицируются.

Источником SD в этом выводе служит **проверенный исходный JMV HDPack с тайлами
128**, как в аудите. Соответствующих страниц в копии JMV textures.res нет.
Одноимённые слоты Base textures.res имеют размер 64 и другие пиксели;
они не использованы как доказательство идентичности. Совпадение имени/слота
между разными банками само по себе недостаточно.

## Метод вариантов

1. Группировка по материалу, проверенному классу и слою. Допускаются только
   подтверждённые static opaque HD256; физические классы доноров прототипа
   внутри каждой группы совпадают. Пулы включают все различные HD исходного
   банка; отдельно проверено, что текущий Dejavu не добавляет иных HD для
   выбранных четырёх случаев. Дубликаты после поворота/зеркала исключаются.
2. Исходные варианты сохраняются. Для каждого нового назначается исходный
   border anchor; все **24 px по периметру** остаются точными пикселями anchor.
   Anchor выбирается циклически между оригиналами. У одноисточниковых материалов
   кромка общая; у многоисточниковых сохраняются существующие семейства кромок.
   Новая универсальная кромка не навязывается уже существующим вариантам.
3. Интерьер собирается четырёхсторонним patch-quilting. Патч **80×80**,
   перекрытие **16 px**; 16 позиций, координаты начала 24/68/112/152 по осям,
   порядок детерминированно перемешан. Для каждой позиции 48 случайных окон
   назначенного донора, включая его D4-преобразования; выбирается минимальная
   RGB-квадратичная ошибка в рамке перекрытия. Четыре минимальных шва считаются
   динамическим программированием, шаг не более одного пикселя. Это локальный
   minimum-error quilting, не глобально оптимальный графовый разрез.
4. Все HD-доноры участвуют в каждом новом варианте. Проверено не только
   назначение доноров: после перекрытия последующими патчами от каждого
   остаются пиксели. Retained counts записаны в traces/metrics.
5. Ранговое сопоставление RGB-гистограмм интерьера с интерьером anchor
   возвращает **точную гистограмму каждого канала всего тайла** и точное среднее
   RGB/яркости. Новой цветовой модуляции нет. Совместная RGB-гистограмма и
   связность тёмных объектов этим не гарантируются; у каменистого грунта
   выявлен именно такой художественный недостаток.
6. PCG64 с фиксированным зерном: `20261011 + sum(slug UTF-8 bytes)*100 + index`.
   Полные зерна и provenance патчей записаны. D4 используется для выбора
   кусочков, но целый повёрнутый/зеркальный тайл новым вариантом не считается.

**Почему 24 px.** В `source/render/tile.cpp:129` inset равен
`(4/512)/(1/8) = 1/16` тайла: 16 px для HD256. Поэтому сохранение лишь
наружных 4–8 px не защищает видимый стык. Полоса 24 px сохраняет ещё 8 px
внутрь от видимой границы, достаточные для данной CPU-проверки и BOX-mip до
32×32. Это минимум 34,0% площади полного тайла, или 13,8% видимой площади
224×224, которые нельзя изменить. Такой объём неизменного рисунка сохраняет
часть сетки принципиально.

**Mip-ограничение:** на 128/64/32 BOX-mip видимые граничные пиксели точны.
На 16×16 максимум расхождения уже **7…11 уровней RGB**. Для production нужно
задавать anchor-кромку отдельно на каждом mip и проверять BC1-блоки и фактическую
фильтрацию. Одного rim24 в mip0 недостаточно для обещания бесшовности на любой
дистанции. DXT1-перекодирование, gutters и игровые mip в этой задаче не создавались.

## Измерения швов, периода и различия

`edge` — средний абсолютный скачок яркости через все 264 стыка области 12×12.
`interior` — средний соседний градиент внутри клеток с inset8;
`ratio=edge/interior`. Это диагностический показатель, не art PASS.
Период: Pearson highpass (RGB Gaussian blur3 → luma subtraction) с лагом
224 px = одна клетка. В JSON есть также 216/232 и 448 px.

Для каждого конкретного сочетания anchor/сосед/повороты разность стыка **точно 0**.

Дополнительная спектральная диагностика: амплитуда гармоники среднего градиента
на периоде 224, делённая на DC. По X/Y: Tundra **0,062/0,062→0,063/0,072**;

Desert HD-контроль **0,016/0,016→0,005/0,004**. Низкое значение не гарантирует
отсутствие узнаваемого орнамента: именно поэтому отдельно просмотрены PNG.

Новая highpass std относительно HD-источников: Tundra **13,14→12,93**,
Brown **27,11→27,13**, Stony **12,90→14,05**, Desert HD-контроль **16,49→16,69**.
Нет размытия на 31%, обнаруженного в stochastic-банке Stage C. Но сохранение
контраста не гарантирует естественную структуру и связность крупных камней.

**Визуальное ревью исследователя:**

- Tundra: внутренние повторяющиеся овалы ослаблены. По углам клеток остаются
  одинаковые тёмные/светлые узлы; сетка видима и по ratio стала чуть сильнее.
  Кусочки исходного узора повторяются внутри нескольких новых вариантов.
- Brown: уменьшился регулярный диагональный рисунок; стыки сравнительно мягкие.
  Светлые щепки и кольцеобразные фрагменты доноров копируются в новые места.
  Это наиболее приемлемый из четырёх примеров, но не новая авторская текстура.
- Stony gray: четыре оригинала уже дают заметное разнообразие. Вариант 5
  меняет мелкий грунт, крупные камни распределяются неравномерно. **Вариант 6
  отклонён художественно:** мелкая чёрная пестрота, заметная прямоугольная граница
  интерьера. Причина согласуется с методом: гистограмма anchor с большими
  тёмными камнями переносится на quilting без сохранения связности этих камней.
  Нужны сохранение крупных объектов или структурно обусловленный подбор
  патчей; увеличение только числа вариантов эту проблему не исправляет.
- Desert: крупный диагональный мотив разбит, резкость камня сохранена.
  Встречаются обрезанные/повторённые трещины и одинаковые угловые «розетки»;
  большой массив всё ещё читается как тайловый. Reused HD пригоден как
  восстановленный источник; автоматическую художественную приёмку пяти
  синтезированных вариантов это не означает.

Следовательно, **отсутствие видимой сетки не подтверждено**. Прототип показывает
снижение периодического повтора при сохранении исходных кромок, а также пределы
этого подхода. Массовый запуск без отбора качества не рекомендуется.

## Полный прогон и размер

Подсчёт заново дедуплицирует декодированные пиксели под всеми D4-симметриями.
Это строже старого аудита, где повторные физические повороты не умножали число,
но совпадение разных изображений после преобразования отдельно не проверялось.
В исходном банке так сняты 25 точных ориентационных дублей; дефицит до шести
увеличился на 10 позиций относительно простого pixel-SHA count.

| Основа | Комбинаций | Требуют пополнения | Недостающих позиций | BC1+mip, МиБ |
|---|---:|---:|---:|---:|
| Исходный JMV, static nonwater, land+overlay | 96 | 90 | 386 | 16,088 |
| Из них только land | 93 | 87 | 375 | 15,630 |
| Текущий подтверждённый Dejavu, static nonwater | 91 | 85 | 360 | 15,005 |
| Из текущих только land | 88 | 82 | 349 | 14,546 |

В исходной выборке число групп с 0/1/2/3/4/5/≥6 HD после D4:
**1 / 44 / 30 / 12 / 1 / 2 / 6**. Единственный нулевой случай — Desert класса 3.
Текущий Dejavu не подменяет полный каталог: пять исходных uniform-комбинаций
там не подтверждены как uniform. Поэтому основной ответ для поручения —
**90 групп, 386 позиций = 385 новых изображений + 1 reused HD**.

Исключены четыре водные поверхности `Water / ...`, а из остальных групп —
все анимированные, неизвестные по анимации и неopaque слоты. Статические
подводные грунты входят. Статические источники Lava Orange/Red (overlay) и
Swamp (overlay) входят только в широкий подсчёт, **не в реализованный прототип
покраски136**, который работает по land. Они дают 11 из 386 добавок и требуют
отдельной политики подключения overlay; анимационные кадры из них не брались.

Расчёт одного BC1 256: девять mip 256…1, минимум один блок 4×4 на уровень,
`Σ max(1, floor((256 >> level)/4))² × 8 = 43 704 bytes`.
Без заголовков/manifest. При самостоятельном append-паке из страниц 8×8
получится **7 страниц, 448 мест**, **18,667 МиБ** BC1-данных всех page mip;
ещё 7×76 байт MMP-заголовков и RES/JSON metadata. Для текущего неполного банка —
6 страниц, около 16,000 МиБ. Это дисковый payload, не пиковая память редактора.
Межматериальный дедуп возможен только с сохранением отдельных semantic keys;
классы нельзя объединять ради экономии.

**Разделение физических классов.** Четыре исходные семантические группы имеют
несколько MP-классов: Grass / Fresh (0,11), Ground / Dead (1,4), Slabs / Square
(2,7), Stone / Red (1,2). Поэтому 386 — ответ в координатах исходного аудита
«материал / reviewed class / слой», не гарантия шести кандидатов для любой
исходной клетки136. Если сохранить каждый физический класс как отдельный пул:

| Основа с дополнительным physicalClass в ключе | Пулов | Нуждаются | Добавок | BC1+mip, МиБ |
|---|---:|---:|---:|---:|
| Исходный JMV, land+overlay | 100 | 94 | 398 | 16,588 |
| Исходный JMV, только land | 97 | 91 | 387 | 16,130 |
| Текущий Dejavu, land+overlay | 99 | 93 | 395 | 16,463 |
| Текущий Dejavu, только land | 96 | 90 | 384 | 16,005 |

После reuse Desert исходному физически разделённому банку требуется до
**397 генераций**. Округление остаётся семь страниц. Эти пулы нельзя молча
склеить при подключении; physicalSplit в budget.json сохраняет полный расчёт.
Прототипы не имеют такого конфликта: у каждого все доноры одного MP-класса.
В текущем Dejavu три таких отдельных пула пока без HD: Ground / Common
(reviewed 0, physical 0), Ground / Dirt (2,2), Rock / Snow (9,9).
Число 395 включает их плановый дефицит, но не доказывает наличие донора
для автоматической генерации. У исходного JMV единственный нулевой пул —
уже разобранный Desert (reviewed 3, physical 2).

Это оценка общего банка, не обещание уместить все добавки в каждую карту.
В карту импортируются лишь необходимые группы с сохранением её slot budget,
анимационных диапазонов и старых слотов. Полный atlas каждого MPR здесь не считался.

Второй детерминированный проход 16 новых тайлов: median **0,139 с/тайл**,
min/max **0,134/0,145 с**, существующий runtime, один процесс. Линейная оценка
самого quilting для 385 тайлов — около **54 с**. Чтение/декодирование,
компрессия BC1, PNG, приёмка и отбраковка сюда не входят; полного генерационного
прогона всех материалов не было. Особенно направленные плиты, мощение,
крупные камни и overlay нельзя принимать по этой оценке времени.

[Постатейный budget.json](../../build-tests-hd-variants-proto/budget.json),
[summary.json](../../build-tests-hd-variants-proto/summary.json).

## Предлагаемое подключение, без реализации

Хранилище: отдельная приватная папка маппера, например
`<mapper>/data/terrain-variants/<bank-id>/`, manifest + пакет
`Ataman_HD_Variants.res`; не игровой HDPack, не автоматическое содержимое Git.
Исходные HD-доноры могут оставаться внешними ресурсами; manifest хранит их
точные SHA и ссылки. Для переносимого offline-банка объём исходных доноров
прибавляется отдельно: приведённый размер относится только к добавкам.

Ключ записи: material identity, reviewedClass, physicalSourceClass, layer,
variant-id, generator revision/seed, hashes доноров и итоговых pixels, anchor
identity, crop/inset, mip policy, разрешённые повороты, weight и статус
художественного отбора. Reused Desert получает отдельный semantic key при
общем HD source hash. Само наличие папки не изменяет карту или мод.

Минимальные места дальнейших изменений:

| Файлы программы | Назначение |
|---|---|
| Новый loader manifest/банка в `source/resources/` или `source/render/`; `source/render/terrain_atlas_presets.cpp`, `terrain_atlas_profile.h/.cpp` | Присоединить проверенный дополнительный банк к глобальным uniform sources и палитре; проверять pixel binding, класс, слой, hash/версию рецепта; хранить anchor/provenance |
| `source/documents/terrain_virtual_atlas.h/.cpp` (CTerrainWorkingAtlas), `terrain_edit_model.h/.cpp` (CTerrainTransitionCatalog) | Импортировать выбранные tiles в рабочий атлас, назначать отдельные physical slots без разрушения старых; точные signatures, weights, class и разрешения ротации; бюджет до мутации |
| `source/documents/terrain_edit_model.cpp` и адаптер покраски `source/render/view.cpp` | Дать selector136 расширенный пул. Его правило «uniform only», раздельный выбор слота/поворота, Undo/Redo, seed и сохранение переходов оставить; зеркала не создавать как SEC-состояния |
| `source/documents/terrain_mixed_edge.cpp`, `terrain_recipe_bake.h/.cpp` | Передавать новые HD в uniformTiles по physical source class; сохранять отдельный reviewed output class. У139 четыре recipe label: шесть доноров не означают автоматически шесть mixed-edge рецептов. Общий anchor кромки должен быть явно согласован и стабилен |
| `source/render/terrain_hd_republish.h/.cpp`, `view_hd_republish.cpp` | Добавить mapper-bank в источники чтения, учитывать его hash в cache key. Для Desert использовать подтверждённую явную связь SD→HD. Синтезированные варианты не выдавать за HD-оригиналы других SD через approximate matcher |
| `source/render/terrain_atlas_archive_binding.*`, `source/documents/terrain_semantic_field_store.*` | Переносить provenance и точную привязку профиля через сохранение/переоткрытие/перепубликацию; старые schema/defaults сохранять |
| `source/resources/mmp_codec.*` и существующие terrain-tests | Проверить финальные BC1-блоки, mip-кромки, readback, публикацию и связанные регрессы на копиях |

Эти файлы только перечислены; реализация не выполнялась. Перед разработкой
нужно решить художественный дефект Stony gray и mip policy. Для136 банк
остаётся набором физических uniform-вариантов; для139 сохраняется отдельный
контракт общей кромки recipe. Уже сохранённые переходы не рандомизируются.
Команда «перевести в HD» должна восстанавливать источник, сохраняя SEC и классы;
добавление разнообразия — отдельное явное действие, а не скрытая перепокраска.
