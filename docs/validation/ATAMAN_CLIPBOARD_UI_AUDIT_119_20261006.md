## Установленная причина

Общий первичный отказ — запись в нативный буфер Windows, до обработки
вставки свойств редактором. `OleSetClipboard` возвращает
`CLIPBRD_E_CANT_OPEN / 0x800401D0`: открыть буфер не удалось.
Qt5.12.12 удаляет переданный `QMimeData` после неудачной записи;
немедленное чтение возвращает пустые данные без MIME типа свойства.
Автотест продолжает цепочку Ctrl+C/Ctrl+V и проверяет значения, которые
в буфер не попали. Поэтому десять false fields являются последствиями
общего отказа транспорта; десять независимых ошибок редакторов не установлены.

К этому приводит воспроизводимая последовательность быстрых нативных записей
без обслуживания событий GUI. Обработка событий между операциями устраняет
все десять исходных отказов, сохраняя обработчики редактора и ожидания теста.
Это не гарантия исправности любой записи: последующие стрессовые операции
тоже иногда получают отказ Windows. Единственная вставка `processEvents()`
не является достаточным надёжным исправлением.

Имя процесса, удерживающего буфер, не установлено. Во время трёх отказов
`GetOpenClipboardWindow()` вернул NULL, PID0. Это не отсутствие блокировки
и не доказательство вины конкретной программы. Полученные данные не
позволяют обвинить Windows history, Codex, антивирус или редактор.

## Первое неверное значение

В `source/app/main.cpp:948` тест записывает несовместимое типизированное
значение; затем `:954` записывает `custom_texture` и сразу посылает Ctrl+V.
Инструментированная собственная копия проверила состояние после записи:

```text
CLIPAUDIT plain-text-set expectedText=0 textLength=0
          hasPropertyMime=0 hasText=0 ownsClipboard=0
CLIPAUDIT texture matches=1 accepted=1 preview=0 currentLength=0
```

Таким образом, стандартная комбинация распознана; значение потеряно раньше.
Та же потеря подтверждена после копирования строки модели, цвета RGB и Z.
При таком состоянии `CTableManager::buildPasteValues` не получает ни
типизированных данных, ни подходящего текста. Для поля модели/текстуры
пустой preview также не может пройти последующий `_onEditingFinished()`.

Места: `source/layout_components/tablemanager.cpp:210` (`copyProperty`),
`:823` (`copyRows`), `:852` (`buildPasteValues`), `:290`/`:413` (компоненты),
`:2392` (фильтр текстового поля). Все эти production-объекты119 повторно
использованы без изменений; изменён только собственный диагностический main.

## Независимый native Qt пробник

Собственный `minimal-clipboard.cpp` использует QApplication/Windows Qt5.12.12,
QClipboard/QMimeData/QLineEdit; код mapper/tablemanager не подключён.
Окна скрыты через `WA_DontShowOnScreen`. Содержимое пользовательского буфера
не выводится; пробник копирует его MIME данные перед началом и выполняет
обратную запись в конце. Полная проверка восстановления всех внешних форматов
не выполнена; ограничение аварийного раннего запуска указано ниже.

В трёх запусках `--tooltip`:

```text
plainImmediate=1 owns=1
newTypedDataDestroyedInsideSet=1
typedImmediate=0 hasType=0 owns=0
lineEditPaste=0
OleSetClipboard: Failed to set mime data (...)
COM error 0xffffffff800401d0
```

GDB подтвердил удаление нового MIME внутри самого `QClipboard::setMimeData`:
`QMimeData::~QMimeData → qwindows.dll → QClipboard::setMimeData`.
Контроль с обслуживанием событий сохраняет MIME и вставляет текст;
`newTypedDataDestroyedInsideSet=0` означает обычное удаление при следующей
замене/завершении, после возврата операции.
Сам Qt/Windows способен корректно копировать/вставлять: первоначальный
отдельный Qt-only прогон, Ctrl+V match и plain/typed/line-edit PASS.
Дополнительный OleInitialize вернул S_FALSE, совместимую уже выполненную
инициализацию; гипотеза отсутствующей OLE инициализации не подтверждена.

Стресс без обслуживания событий:100 последующих записей,100 отказов.
С одним проходом `processEvents`:100 записей,3 отказа в данном прогоне.
С20мс event-loop перед каждой записью: три прогона по100 записей,
4/3/7 отказов. Эти результаты не являются PASS и показывают необходимость
проверки результата и повторной записи с обслуживанием событий при отказе.

Сопоставление с первичным исходником Qt:
[qwindowsclipboard.cpp v5.12.12](https://raw.githubusercontent.com/qt/qtbase/v5.12.12/src/plugins/platforms/windows/qwindowsclipboard.cpp),
`setMimeData`: до трёх попыток `OleSetClipboard`, блокирующий `msleep(100)`
при `CLIPBRD_E_CANT_OPEN`, затем диагностическое сообщение и `releaseIData`.
При locked-session попытки могут закончиться раньше. `mimeData` возвращает
собственный MIME лишь при `OleIsCurrentClipboard == S_OK`.
Использованный qwindows.dll byte-identical SDK, SHA256:
`2E7DAACB512065E19751E0CCE40B23506EC7E1A2F0C6D541B85061868995AD56`.

## Границы результата и следующий шаг

Причина первого неверного значения и общая причина десяти отказов установлены.
Это не ручная приёмка всех clipboard-сценариев установленного редактора.
При аналогичном отказе Windows обычная операция копирования редактора также
может потерять данные: `setMimeData` возвращает void, production helpers
не проверяют readback. Автотест особенно легко вызывает эту ситуацию.

Нужное исправление: синхронизировать операции теста с циклом событий и
проверять готовность/readback буфера; при отказе повторять запись новой копии
MIME с обслуживанием событий и ограниченным deadline. Отделять отказ
clipboard precondition от ошибки обработчика свойства. Отдельно обеспечить
и проверить восстановление пользовательского буфера. Не заменять это
фиксированным `Sleep`, ослаблением assert или признанием отказов PASS.
Целесообразно покрыть прямую запись, Copy через клавишу и Qt line-edit,
контекстное меню, цвет, координаты и явную временную блокировку Windows.
В production copy/paste нужна видимая диагностика неудачной записи.
Реализация этого исправления текущим поручением не запрошена.

Один ранний запуск инструментированного probe завершился access violation:
добавленная диагностика читала MIME после передачи владения Qt, который уже
удалил его из-за неудачной записи. Пробник исправлен; этот запуск не PASS
и не доказывает новый crash установленного редактора. Полное восстановление
буфера после аварийного запуска не подтверждено; дальнейшие пробники не
используют переданный Qt указатель повторно. Логи/дампы и бинарные пробники
остаются локальными в ignored build-каталоге и не предназначены для ZIP/Git.
