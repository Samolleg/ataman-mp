## 1. Семантика маппера привязана к SHA всей MPR

В [`CView::buildTerrainSemanticFieldMember`](../../source/render/view.cpp)
(13947) JSON `ei_terrain_semantics_<namespace>_<identity>.json` содержит
полный SHA256 кандидата MPR (13971), кроме полей материалов земли/покрытий,
размерности, SHA атласа и профиля. Эта запись предназначена для восстановления
точных материалов общих углов, включая неоднозначные переходы.

Уточнение пользователя2026-10-07: зачем хранить контрольную сумму. Это
проверка принадлежности служебного поля текущей версии покраски: после замены
MPR или изменения её тайлов вне этого сохранения нельзя применять прежние
материалы углов без проверки. JSON используется только маппером
(`terrain_semantic_field_store.h:11`); загрузка проверяет binding до восстановления
полей (`view.cpp:14056`). Защита нужна, но SHA всей MPR учитывает лишние данные:
высоты не определяют принадлежность материалов. Будущая привязка должна
проверять данные тайлов/материалов, атлас, профиль и размерность без высот.

Изменение только высоты меняет SEC payload, значит и полный SHA MPR. Поля
материалов остаются прежними, но JSON получает другой `mprSha256`.
[`validateBinding`](../../source/documents/terrain_semantic_field_store.cpp)
(154–167) требует точное совпадение этого SHA. Прежнюю запись после сохранения
новой высоты маппер отвергнет при повторном открытии.

Обычный changed save в `source/render/view.cpp:10562` готовит эту запись
независимо от того, были ли изменения материалов. При наличии активного RES
вызывается публикация члена (10610–10633). В
[`commitStagedResPublishedMembers`](../../source/documents/res_save_coordinator.cpp:213)
строится полный кандидат RES; no-op определяется сравнением всех байтов
кандидата с назначением после перестройки (265). Новый `mprSha256` исключает
no-op. Весь архив проходит staging/backup/atomic replacement ради одной записи.

Поэтому перезапись RES сама по себе не означает, что покрашены или изменены
пиксели текстур. Для полностью неизменных материалов эта зависимость от высот
избыточна. Просто пропустить запись при прежней схеме нельзя: при reopen
старая семантика перестанет проходить проверку.

## 2. Рабочий профиль принудительно запускает публикацию атласа

[`terrainMprSaveRoute`](../../source/core/terrain_save_flow_policy.h:45)
выбирает `PublishModernAtlas`, если `persistedWorkingDraft=true`, даже без
новых extensions и запроса сменить identity. Этот параметр вычисляется по
типу загруженного профиля в `source/render/view.cpp:9926`.
В `saveLand` маршрут запускает `finalizeVirtualTerrainAtlas` (9820–9828).
Здесь перепубликовываются страницы и профиль вместе с MPR.

Журнал постоянной установки подтверждает этот маршрут для zone9:

- `logs/workflow.log:12253`,2026-10-07 10:43:00:
  `persistedDraft:true route:publish-current-target`.
- Там же12321,10:43:23: успешная публикация в текущий MPR и
  `HDPack_Terrain.res`, identity `zone9_f24337452d99`.

Для общей кисти есть дополнительная ветвь
[`saveWorldTerrainMaps`](../../source/render/view_world_terrain.cpp:312):
наличие `doc->atlas`, а не отдельный признак изменения пикселей, запускает
подготовку страниц/профиля (335–387), затем обновление semantic JSON (396–407)
и общего RES (413–421). Неизменные страницы сравниваются и не перекодируются
в page patch loop, но запись семантики и сборка RES всё равно возможны.
