## Причина и исправление

Трассировка исходного пути общей кисти показала1323/1427ms в load-library.
Одна точная привязка RES занимала600–740ms, из них145–224ms декодирование
и380–534ms SHA-256 полного атласа. Проверка повторялась при новом сочетании
материалов и на соседней карте: staging получал общие кэши, но терял новые
проверенные привязки и пиксели после мазка. Сам resolve не объяснял паузу.

- Системный Windows CNG вычисляет тот же SHA-256 над прежним потоком: число
  изображений, размеры RGBA8888, строки без padding. При недоступности/ошибке
  провайдера весь поток повторно вычисляет прежний QCryptographicHash.
  Библиотека загружается только по абсолютному системному пути. Требование
  к автоматическому буферу BCryptCreateHash проверено по
  [документации Microsoft](https://learn.microsoft.com/en-us/windows/win32/api/bcrypt/nf-bcrypt-bcryptcreatehash).
- Общий потокобезопасный кэш ограничен128 digest и256 записями привязок.
  Ключ включает путь, идентичность/версию файла, namespace и геометрию атласа.
  Он хранит фактический SHA, не результат сравнения с ожидаемым хэшем.
  Windows epoch включает volume/file ID, размер, LastWriteTime и ChangeTime;
  повторная проверка после чтения исключает подмену в ходе проверки. Если
  сильная версия файла недоступна, общий digest не переиспользуется.
- Общая кисть сохраняет проверенные привязки/пиксели между картами и мазками.
  Выбор источников материалов остаётся локальным для карты. Перед возвратом
  сохранённых пикселей проверяется актуальность привязки RES. Транзакции
  атласа, история, сохранение и алгоритм переходов не заменялись.
- Добавлены адресные фазы terrain-bind-exact, terrain-source-tile и
  terrain-realize-signature в существующую диагностику долгих операций.
