# EI-TERRAIN-PIPELINE-AUDIT-20261020 — текстуры, переходы и атлас Ataman209

## Для владельца: как это работает

Маппер хранит отдельно **материалы углов клетки** и **готовые картинки тайлов**. Кисть назначает материал вершинам или четырём углам клетки. Для получившегося сочетания четырёх материалов программа сначала ищет подходящую готовую картинку в карте, затем в проверенном JMV-каталоге. Если её нет, составляет новую из однотонных по материалу исходных тайлов и маски перехода. Новые картинки попадают в рабочий атлас в памяти. При сохранении209 оставляет необходимые тайлы, упаковывает их по64 на страницу, перенумеровывает ссылки SEC и публикует MMP вместе с MPR и описанием материалов. Страницы128 и256 пикселей на тайл хранятся раздельно, в одной карте допускаются оба размера.

**Прежнее массовое размножение HD-тайлов в209 исправлено. Проверенные42 карты сейчас не превышают ограничений страниц/overlay. Однако утверждать «проблем точно нет» нельзя: остаются дорогая публикация, смена namespace без изменения картинок, накопление внешнего recovery и неполная гарантия визуального совпадения краёв соседей.**

## 1. Откуда берутся материалы и картинки

### Ресурсы и приоритет

`source/resources/resource_profile.cpp:372` разворачивает профиль. Для переносимого Dejavu/JMV используются `{modRoot}/res`, затем `{gameRoot}/Base/Res`, и соответствующие Maps. Фактические настройки установленной209: профиль `deja-vu`, `C:/GOG Games/PZ/MODS/DejaVu/res` и `C:/GOG Games/PZ/Base/Res`.

`source/resources/resourcemanager.cpp:292` берёт `resourceRoots`, при отсутствии — прежние figPaths/texPaths. `source/resources/resource_name.cpp:93` сохраняет порядок каталогов, явные RES, порядок секции RES в config.ini, затем добавляет остальные `*.res`. Выигрывает первый найденный member (`resourcemanager.cpp:170`). Поэтому это не жёсткое правило «всегда только два файла»: каталоги могут содержать дополнительные RES. Таблицы RES индексируются без чтения всего payload, кэшируются по path/size/mtime (`:127`); имена архива декодируются CP1251 (`:155`).

Фактически для исследованных карт numbered MMP найдены в текущем `DejaVu/res/HDPack_Terrain.res`, Base `textures.res` скопирован как нижний источник. В настройке `terrainAuthoringArchive` отдельно указан установленный `terrain-reference/HDPack_Terrain-JamaisVu135-50c285225fb1745e.res`, SHA256 `50c285225fb1745ee70d280e57a214f346481e6d380a78d55475f730d11a81b2`. Это эталон **авторского арта для кисти**, а не целевой пак публикации. `resourcemanager.cpp:1792–1828` читает его путь и проверяет SHA с кэшем ревизии файла. Сам каталог материала загружается из встроенного `:/terrain_atlas_presets.json` (`terrain_atlas_presets.cpp:14–42`).

Отдельный `<mpr>-atlas.res`/подтверждённый map-local архив ищется перед общими игровыми ресурсами (`resourcemanager.h:191`, `.cpp:1831`, `:1929`). Привязка профиля проверяет **весь набор страниц одного архива** и hash декодированных пикселей, не смешивает страницы разных физических ревизий (`terrain_atlas_archive_binding.cpp:433–558`). Наличие одинакового имени member само по себе недостаточно.

### Три разных значения слова «материал»

1. **Материал кисти/угла:** глобальное семейство, например Grass / Dark. Global ID = FNV-1a от нормализованного имени + land/overlay, с положительной областью `0x40000000...`; namespace и прежний localFamilyId в ID не участвуют (`terrain_atlas_presets.cpp:98–115`). Коллизии и несовпадения runtime-класса диагностируются (`:204–218`). Палитра группирует по теме, но разные оттенки/вариации с разными именами остаются разными материалами.
2. **Игровой класс слота:** `MP.tileTypes[slot]`, целое0–15. Он влияет на игровую поверхность; одинаковые пиксели не означают одинаковый класс. Не путать с таблицей `MP.materials`, используемой overlay и содержащей цвет/прозрачность/волны/warp/свечение. При generated-переходе класс выбирается большинством углов; при равенстве требуется класс текущей кисти/предшественника, иначе отказ (`terrain_virtual_atlas.cpp:2993–3043`).
3. **Класс рендера:** opaque/cutout/transparent, определяемый alpha-содержимым DXT/картинки (`resourcemanager.cpp:42–118`). Это ещё один признак, не глобальный ID и не индекс overlay-материала.

**Сигнатура тайла** — NW,NE,SE,SW из четырёх semantic ID (`terrain_edit_model.h:78`). В JSON углы заданы в пространстве предпросмотра; каталог переводит их в сетку, отражает Y и регистрирует4 допустимые ориентации без4 физических копий (`terrain_atlas_profile.cpp:1569–1593`). Вращение не меняет сам смысл материала. Профиль сначала ищется как явный override/embedded, затем exact preset по namespace+pixel hash; только при отсутствии предлагается вывод по цвету/фактуре углов, классам и использованию. Неуверенные слоты помечаются ambiguous/unassigned (`view.cpp:12064–12148`, `terrain_atlas_profile.cpp:1910–1939`, `:2037–2117`). Это не распознавание материала по имени файла MMP.

Game-wide palette берёт uniform-слоты с четырьмя одинаковыми углами и проверенные HD bindings. Картинка thumbnail сама по себе не выдаёт право красить; семейство без настоящего uniform не получает обычный глобальный brush (`terrain_atlas_presets.cpp:129–180`). В замере загрузилось38 exact bindings,88 material sources/thumbnails. Для альтернативных отвергнутых ревизий остаются35 шумных предупреждений; пригодность другой правильной ревизии они не отменяют. Это согласуется с предыдущим read-only разбором `ATAMAN_HD_BINDING_WARNING_AUDIT_20261019.md` и текущим журналом.

Это отдельные приватные данные установки, не атлас открытой карты:

- `hd-library/index/`: сохранённый индекс сопоставления. Текущая функция190/209 непосредственно его не читает: её зависимости — sources/manifest и банк вариантов.

Группа хранит material/layer, physicalClass/reviewedClass, originals с namespace:slot:pixelSHA, число generated/rejected/shortfall. В entries — ключ группы, anchor, слот и SHA пикселей; в pages — файл/размер/SHA; inputs связывают исходный member с локальным архивом.
-209 **потребляет готовый банк**, проверяя SHA страниц/пикселей и native HD anchors (`terrain_base_hd.cpp:63–161`). Нового texture-quilting генератора банка в текущем `source` нет. ### Где JSON и что внутри

Профиль schema10 содержит namespace, ordered atlasPixelSha256, число страниц/слотов, provenance, approved, resourceArchiveHint, paintReferenceSha256; семейства с allowedLayers/underwaterRole/tileType/thumbnail/memberSlots; слоты с signature/assigned/ambiguous/paintSelectable/referencePaintSelectable, routeOwnerMaterial и при наличии sourceNamespace/sourceSlots/sourcePixelSha256 (`terrain_atlas_profile.cpp:260–338`). Пиксели в этот JSON не кладутся.

Пути:

- встроенные defaults: `data/terrain_atlas_presets.json` через Qt resource;
- явные overrides установки: `<app>/terrain-atlas-profiles/<namespace>-<hash>.semantic-atlas.json`;
- рядом с картой: `<Maps>/terrain-atlas-profiles/<map>-<hash(namespace+filename)>.semantic-atlas.json` (`terrain_atlas_profile.cpp:1271–1302`);
- опубликованный профиль внутри RES: `ei_atlas_profile_<readable namespace>_<hash namespace16>.json` (`:972–985`);
- semantic field — отдельно: `ei_mapper_terrain_semantics.json` внутри MPR и связанный JSON в RES. Там размеры сетки, hashes привязок и land/overlay массивы32-битных ID, qCompress(level9)+base64 (`terrain_semantic_field_store.cpp:26–65`, `:75–112`, `:223`, `:346`). Это поле углов, не набор копий текстур.

## 2. Покраска и рабочий атлас

`CTerrainVirtualMaterialField` хранит материалы вершин; `CTerrainWorkingAtlas` — физический кэш показанных/используемых картинок. Исходные authored-слоты внутри сеанса неизменяемы. Рабочая адресация до16384 слотов допускает больше конечного лимита126 страниц; это предел формата packed tile, а не обещание совместимости с оригинальной игрой (`view.cpp:12393–12424`, `terrain_virtual_atlas.cpp:4374–4411`).

Нажатие начинает один stroke, фиксирует режим/слой/материал и seed. Seed = семантический seed карты XOR случайный nonce мазка XOR номер команды; Undo/Redo воспроизводит записанные packed значения, не бросает случайность повторно (`view.cpp:21336–21403`). Координаты клетки получаются pickTile; semantic Vertex привязывается к ближайшей вершине двухметровой сетки, Tile — к клетке, круг/квадрат и радиус задают footprint (`:18948–18984`). Промежутки между событиями кисти заполняются линией вершин (`terrain_edit_model.h:70`). Первый stamp откладывается, если commit footprint не совпал с показанным hover (`view.cpp:19490–19503`). Это было причиной неприменения первого действия в измерительной обвязке, не дефектом209.

| Режим209 | Что делает |
|---|---|
| Modern, автопереходы включены | Назначает виртуальные материалы углам/вершинам, находит все затронутые клетки, реализует недостающие exact-сигнатуры, объединяет preview и переходы в одну команду (`view.cpp:13034–13132`, `:19990–20027`) |
| Modern, автопереходы выключены | `makeUniformTilePaint`: раскладывает uniform-картинки по footprint. Переходы не дорисовываются этой операцией (`:19985–19989`) |
| Classic | Карта-локальный каталог готовых переходов. Safe = ExactExistingOnly с пропуском неподдерживаемых участков; обычный режим разрешает локальные жёсткие края. Контекстные материалы могут пользоваться support-материалом (`:19783–19842`, `:19961–19983`) |
| Manual | Выбранные физический slot+rotation, без semantic-автоподбора. При общей кисти реальная картинка импортируется в атлас соседа, его номер слота не копируется вслепую (`view_world_terrain.cpp:1043–1057`). Обычная ручная покраска может сознательно создать визуальный шов |

Modern и Classic действительно есть в209. Отсутствует запрещённое новое ядро Modern mixed-edge/B1/B2.

При первом нужном сочетании импортируются проверенные uniform или готовые stock-варианты. Для данного exact-сочетания могут реализоваться **все** подходящие authored-варианты, а не только выбранный для одной клетки (`view.cpp:14495–14542`, `terrain_virtual_atlas.cpp:4813–4836`, `view.cpp:14677–14695`). Они нужны разнообразию кисти, но временно занимают больше памяти/слотов. Рабочий `realize` использует свободное расширение, учитывает usage и Undo-защиту, удаляет старую working mapping при вытеснении (`terrain_virtual_atlas.cpp:5442–5508`). Физический импорт не создаёт4 копии для поворотов: четыре каталожные записи адресуют одну картинку (`:5661–5708`).

## 3. Переходы: точный порядок и генерация

### Stock и exact

Порядок задан в `view.cpp:14457–14605` и `terrain_virtual_atlas.cpp:3067–3238`:

1. Уже имеющийся точный tuple в текущем paint-каталоге с нужным игровым классом/допуском.
2. Exact authored transition из проверенного JMV global-каталога. Сначала проверяется цельная физическая ревизия; при настроенном эталоне выбирается один согласованный банк. Картинка берётся из его MMP-слота, а поворот — из каталоговой записи.
3. Generated exact blend из uniform sources всех участвующих материалов. Нет исходника, маски или однозначного runtime type — операция отказывает; другой материал вместо запрошенного не подставляется.

Stock blend — готовый арт JMV, он не вычисляется повторно по похожим цветам. Exact означает совпадение четырёх semantic ID и ограничений класса/происхождения. Это **не** доказательство пиксельного совпадения с произвольным соседом.

### Как составляется новая картинка

`CTerrainVirtualAtlas::generateTile`, `terrain_virtual_atlas.cpp:2667–2860`:

- Размер — размер нормализованных source tiles resolver. В mixed-карте используются synthesis/display tiles максимального размера256; native128 не заменяются в сохранённом источнике. На полностью SD входе возможен128. `CTerrainWorkingAtlas` передаёт `terrainDisplayTiles(authoredImages)` (`:4402–4405`, `terrain_image_sizes.h:7–27`).
- Для каждого уникального материала выбирается один uniform source. Приоритет имеет локальный uniform открытой карты; внешний проверенный источник заполняет нехватку (`:2087–2129`). Поэтому одинаковый global ID на двух картах ещё не обещает один и тот же исходный рисунок.
- Для пары материалов берётся grayscale ownership-mask и её инверсия. Для3–4 материалов — по полной маске для каждого распределения углов, затем нормализация весов. Пробел нулевого веса закрывает bilinear-разделение углов. В перекрытии оставляются два сильнейших материала, смешивание сужается до интервала0,38–0,62 со smoothstep (`:2701–2748`, `:2776–2823`).
- В пикселе(x,y) читаются пиксели **тех же(x,y)** из uniform sources. Их RGB смешиваются по этим весам; это не копирование готового stock перехода и не quilting. Production смешивает кодированные RGB, linear-light доступен только review-методом (`:2760–2763`, `:2855–2858`, `:128–160`, `.h:289–295`). Для земли прозрачные BC1 texels заменяются непрозрачным материалом, чтобы не получать дыр (`:408–456`).
- Обычные2-материальные topology: внешний угол1/4, противоположность3/4, соседняя пара2/4, диагональная пара2/4. Стиль grass/soil/ice/lava/paving/stone/gravel/sand/snow/swamp/water выбирает язык маски.
- Приоритет — встроенные проверенные PNG256×256 с жёстким pixelSHA и provenance. Их отражают поY, поворачивают до совпадения углов, при128 уменьшают SmoothTransformation, при смене владельца инвертируют (`:1261–1343`). Действуют перечисленные в коде authored-derived маски R44/R71/R75/R76/R77 и последующих решений, в том числе R155 stone-edge. Имена исторических решений в строках не означают наличие нового RecipeBaker.
- Если применимого reviewed-asset нет, используются процедуры131: внешний угол — суперэллиптическое расстояние с синусоидальным смещением, соседняя пара — граница около0,5 с нечётной волной, диагональ — седловая функция. Параметры стиля задаются `:486–591`, формулы `:600–718`. Для1/4 и3/4 используются поворот/инверсия базового угла. Fallback защищает corner patches примерно1/16 стороны (`:1346–1421`).
- Подготовленные stock mask templates сохраняются как калибровочные данные. Они не подменяют canonical ownership используемой generated-ветки (`terrain_virtual_atlas.h:262–265`).

Ключ generated-кэша включает канонизированную по поворотам сигнатуру, style, variation, reviewedStyleMaterial, routeOwnerMaterial и runtimeType. Затем есть pixel-hash dedup с сохранением семантики/класса/route owner; одинаковые RGB разных смыслов не сливаются (`terrain_virtual_atlas.cpp:3141–3238`).

### Края и отказы

На **самом внешнем кольце texel** compositor задаёт общий smoothstep-профиль по двум материалам концов ребра, независимо от внутренней вариации (`:2825–2854`). Но рендер использует inset1/16 тайла, то есть16px при256. Внешнее кольцо — gutter, а не видимая линия контакта. Это прямо учитывает `joinAuthoredTransitionEdges` (`:4969–5008`).

Join не рисует новые края. Он отбирает готовые кандидаты с той же сигнатурой, классом и route provenance, измеряет по16 усреднённых RGBA-проб на видимых рёбрах, оптимизирует цепочки строк/столбцов, максимум8 проходов. Единственный кандидат и uniform-клетки могут пройти без оптимизации; финальная ошибка не сверяется с обязательным порогом (`:4931–4967`, `:5051–5157`). Поэтому гарантия «совпадут все края» из кода не следует.

Отказы/пропуски происходят при недоступном exact reference/source, неизвестной сигнатуре/классе, равенстве классов без tie-break, отсутствии вместимости/свободных незащищённых слотов, неподдерживаемом semantic field, неудаче загрузки GPU/preview или несовпадении live режима с началом мазка. Stamp готовит semantic model на копии, но отдельные cache-импорты могут уже остаться при последующем отказе (`view.cpp:13046–13125`). Их наличие не равно записанному повреждению карты.

### «Исправить переходы» и соседние карты

Одиночный Resolve работает для Ground и Overlay: восстанавливает исходное material field по физическим сигнатурам на staging-копии, сохраняет спорные общие углы, собирает недостающие сочетания, реализует их, применяет одну Undo-команду только после подготовки/preview (`view.cpp:20793–21290`). Это ремонт представления известной семантики, не новая глобальная перекраска и не автоматическое угадывание стороны спорной границы.

Общий Resolve обходит связанную группу включённых общей кистью соседей, восстанавливает каждую карту со **своим** атласом, согласует однозначные граничные материалы; конфликт сохраняет и сообщает. У соседей меняются только клетки общих краёв, у активной карты возможен обычный проход исправления (`view_world_terrain.cpp:793–918`). После штатного131 resolver код намеренно не делает второй генератор/перерисовку collar (`:924–926`). В этой ветке отсутствует парный вызов `joinAuthoredTransitionEdges` с border-картинками соседей.

При общей **покраске** обе стороны сначала готовятся независимо. Затем из atlas соседа читается его реальный QImage+rotation; собственные локальные номера слотов не сравниваются. До4 проходов парного подбора уточняют видимые стыки (`view_world_terrain.cpp:1117–1167`). Это правильная защита от подмены чужого slot своим, но всё ещё минимизация ошибки, без строгого согласования pixels или общего источника каждого материала. Ветка `loadWorldTerrainMaterialSources` умеет детерминированный общий источник (`view.cpp:14389`), однако сам факт наличия этой функции не доказывает, что описанные brush/Resolve заменяют ею все локальные resolver anchors: в просмотренных путях такого вызова нет.

**Ограничение проверки P3:** реальные карты измерялись по отдельности. Новая двухкарточная visual/game acceptance общей кисти не выполнялась. Найдено конкретное отсутствие строгого критерия/парного join в Resolve, а не объявлено повреждение конкретной границы кампании.

### Вода и анимации

Flipbook задан MP как startSlot+frameCount; активация — только по startSlot, одинаковые кадры не должны схлопываться в static alias (`overlay_material_animation.cpp:94–120`). `CTerrainWorkingAtlas::normalizeAnimationRanges` восстанавливает непрерывный диапазон внутри одной страницы (`terrain_virtual_atlas.cpp:4497`). Compact удерживает **все** объявленные диапазоны, даже временно не используемые; сохраняет фазы, старт и класс. Диапазон больше64 или через разные native sizes отклоняется (`terrain_atlas_compact.cpp:102–120`).

Отдельно material animation задаёт waveMultiplier/warpSpeed, анимацию типов2/3 (`overlay_material_animation.cpp:83–92`). Прозрачность/свечение/деформация поверхности остаются в материалах MP и геометрии, не запекаются в новый номер семантического материала. HD-конверсия исключает overlay-used слоты, анимационные диапазоны, underwater/Water и класс6 (`terrain_base_hd.cpp:140–149`, `:176–190`). Она не создаёт новые анимационные фазы воды.

## 4. Запись MPR/RES и три команды обслуживания

### Формат и размеры

MPR — контейнер RES с MP/SEC и другими членами. MP хранит nTexture/textureCount, textureSize, nTile/tileCount, tileSize, таблицу материалов, класс каждого логического слота и анимации (`mpr_document.cpp:350`, `.h:69–89`).

Packed tile SEC =6 бит tileIndex(0–63),8 бит atlasIndex(0–255),2 бита rotation; slot=page×64+tile (`mpr_document.cpp:168–181`). Номера слотов локальны для namespace, имя MMP =`<namespace><page:003>.mmp`. В overlay дополнительно хранится signed material index; отрицательный означает отсутствие активного покрытия и не должен удерживать мусорный tile.

Каждая MMP —8×8 тайлов **одного** native size:1024² для128px или2048² для256px. Native payload DXT1/BC1 имеет76-байтный заголовок и mip chain. Разные размеры страниц одной карты допустимы для текущего mapper; MP209 после compact описывает **максимальный** размер, а не размер первой страницы (`terrain_atlas_compact.cpp:185–189`). Это не256px для каждого физического SD-слота. Последний физический лист содержит padding; логический nTile в старом MP может быть меньше64×pages, но compact209 выравнивает новую таблицу на физические страницы.

### Finalize и compact209 — разные этапы

Virtual finalize разрешает поле материалов, удерживает pinned artwork/анимации, умеет сливать точные authored outputs только с совпадением класса/смысла и сохранять source aliases; анимационные фазы не сливаются (`terrain_virtual_atlas.cpp:3338–3455`). Portable package записывает MP/SEC и MMP (`:3812`, `:4072`).

Compact209 работает по **уже подготовленным физическим страницам**. Он проверяет целиком pixel binding профиля, удерживает land и активные overlay SEC, thumbnails, по одному selectable uniform seed на семейство/native-size/class/reference-eligibility и все animation ranges. Origin/aliases — метаданные, не причина сохранять старый физический слот (`terrain_atlas_compact.cpp:40–120`). После разбиения по128/256 анимационные блоки кладутся целиком, статические слоты плотно. Проверяется конечный предел126.

Independent BC1-блоки переносятся без переквантования до page mip32×32 включительно; меньший общий mip-tail16..1 пересобирается. Поэтому «побайтно сохранён весь старый MMP» к compact не относится; сохраняется арт отдельных тайлов/его независимые уровни (`:147–171`). Переписываются MP, обе активные SEC-таблицы и animation starts; rotation остаётся прежней (`:178–195`). Сигнатуры/семантика переназначаются и заново связываются hashes (`:196–207`).

Обычный Save теперь входит в working-atlas pipeline даже без видимых новых переходов (`view.cpp:10349–10401`). Он строит working preview, декодирует physicalDraftTiles, создаёт профиль, вызывает `compactTerrainPublication(...forcePublication=true)` (`:10465–10531`, `:10608–10617`; `terrain_atlas_compact.cpp:412–421`). Поэтому дешёвый no-op кнопки compact не означает дешёвый no-op обычного Save. Перенумерация начинает новую историю редактирования; прежние Undo-команды нельзя применять к новым slot numbers.

### Namespace, предел и сохранность

Собственный namespace генерируется как baseName+12hex content hash. Голый исходный namespace больше не расширяется обычной публикацией209. Даже компактный голый atlas кнопка compact переводит в собственный hash (`terrain_atlas_compact.cpp:137–145`, `:174`). Обнаруженный P2: content hash включает сериализацию входного профиля и старого MP; оба уже содержат прежнюю идентичность. Поэтому следующий save способен получить другое имя при тех же MMP.

Издание больше126 страниц отклоняется (`terrain_atlas_compact.cpp:331–334`),100+ вызывает предупреждение (`view.cpp:10612–10614`). Есть независимые guards общего final-save validator/координаторов (`staged_save_validator.cpp:116`, `:322`, `:892–897`). Промежуточная транзакция может превышать лимит до compact. Открытие большой исторической карты для диагностики и рабочий кэш до256 страниц сами по себе не разрешают её опубликовать. На GPU есть другой предел максимальной ширины/высоты texture grid (`landscape.cpp:467–479`), который может сработать раньше ограничения адресации формата.

Для обычного Save: подготовка MPR/RES и metadata, durable atlas recovery, backup старого RES, атомарная запись/проверка RES, backup/атомарная запись MPR, принятие baseline, затем условное удаление старого hash namespace (`view.cpp:10618–10747`). Откат при неудаче предусмотрен; RES и MPR не являются одной атомарной файловой операцией. Во время прерывания между ними новый namespace уже может лежать в RES, а прежняя MPR продолжит ссылаться на старый; это восстановимый лишний ресурс, не основание заранее удалять старый.

Удаление старого hash выполняется **после** успешной новой пары и сверки читаемых MPR каталогов. Если другой MPR использует имя, инвентарь неполный/изменился, каталог недоступен или это голое имя — сохранить (`terrain_atlas_compact.cpp:223–236`, `:399–409`). Save As сохраняет исходную публикацию для исходной карты. Поиск каталогов — эвристика расположения mod/Base/Maps, а не поиск по всему диску (`:336–343`). Внешние копии карт вне этих каталогов в инвентарь не входят: это граница разрешённой уборки, не глобальный реестр всех ссылок.

### Автосохранение, recovery, backup

Автосохранение не меняет campaign MPR/HDPack. Оно готовит связку MPR+собственный RES с профилем и семантикой в фоне, пропускает устаревший результат при изменении source SHA (`main_window.cpp:8328–8365`; `view.cpp:10219–10303`; `backup_manager.cpp:145–197`). Сохранность generation проверяется по hashes пары. Удерживается20 autosaves на источник; pre-save backup —50, open snapshot дедуплицируется (`backup_manager.h:61–62`, `.cpp:249–263`, `:600–611`).

Другой механизм — `backups/terrain-atlases/{objects,manifests}`. Большие страницы/profile/semantic content-addressed; одинаковые blobs переиспользуются с readback SHA, manifest привязан к atlas+MPR hashes (`terrain_atlas_recovery_store.cpp:82–112`, `:144–238`). Его поколения и blobs **не охвачены** указанным20/50 retention и не имеют своей GC-команды (`.h:41–73`). Это P5; нельзя удалять blobs только потому, что соответствующий namespace исчез из игрового пака: они могут понадобиться сохранённым резервам.

### Кодировка журналов

В `source/core/log.cpp:50–65` создаётся новый QTextStream без setCodec, пишет системной кодировкой. В текущей среде `QTextCodec::codecForLocale()->name()` вернул `System`. Реальные байты после `Base HD conversion completed:` начинаются `c7 e0 ec e5 ed e5 ed ee` — это «Заменено» в CP1251, а не повреждённый UTF-8. CP1251 возвращает всю строку «Заменено клеток...», UTF-8 с replacement даёт `�`. [log-encoding.json](../../build-tests-terrain-audit/log-encoding.json) сохраняет исходные hex и оба прочтения. Первоначальная гипотеза HANDOFF об уже испорченном UTF-8 для этих строк не подтвердилась.

Предложение: явно UTF-8 для новых журналов и метка/различение старых CP1251 при чтении. Уже прочитанные replacement-строки нельзя перекодировать обратно без исходных байтов; оригинальные просмотренные logs позволяют корректное чтение. Ошибка не затрагивает бинарные MMP/SEC и JSON, сериализуемый QJsonDocument.

### Где расходуются ресурсы

**Открытие.** Чтение SEC/MP мало по сравнению с подготовкой картинок и палитры. В core замере decode+SHA всех1216/3456 tiles заняли0,639/2,370с с удержанием172/636МиБ native images. Exact-binding кэш и принятие уже декодированных tiles существуют (`terrain_atlas_archive_binding.cpp:163–184`, `:470–558`; `view.cpp:12029–12036`). Каталог отложен до первого кадра либо явного interaction (`terrain_catalog_load_policy.h:11–25`); deferred global hydration запускает2 потока и проверяет альтернативы.

**Mixed-size display.** `resourcemanager.cpp:1995–2026` декодирует все страницы, SD увеличивает до максимального разрешения и создаёт общий RGBA canvas. На zone3 layout8×7 по2048 =16384×14336 =896МиБ только база этой картинки, до mip/копий драйвера. Native636МиБ — другая величина. Дополнительно normalized resolver images и preview snapshots (`terrain_image_sizes.h`, `terrain_virtual_atlas.cpp:4402`, `landscape.cpp:433–460`). Одноразмерный desktop GL имеет compressed-DXT upload (`resourcemanager.cpp:2137–2149`); нельзя приписывать ему ту же обязательную RGBA-схему, а тем более автоматически переносить этот вывод на игровой renderer.

**Покраска.** Есть prewarm, staging-copy, scan usage/защиты и dedup необходимых сигнатур. Стабильный layout позволяет in-place upload изменённых tiles; при увеличении grid возможен GPU regrid-copy, затем full-upload fallback (`landscape.cpp:481–508`). Это уже полезная оптимизация209. У общей кисти usage сканируется для каждой карты, хранятся before/after atlas snapshots; память зависит от числа участников и новых картинок, а не только radius (`view_world_terrain.cpp:1014–1034`, `:1170–1181`).

**Save/публикация.** `view.cpp:10487–10531` строит пакет, снова декодирует все физические slots и строит JSON; compact снова сверяет полный source pixel hash и собирает новый atlas/profile. Затем весь HDPack читает `readAll`; `CResArchiveDocument::loadBytes` делает `bytes.mid` для payload каждого member и hash (`res_archive_document.cpp:68–130`). Координатор создаёт новый полный RES, stage, fresh reopen, backup, atomic commit/readback (`res_save_coordinator.cpp:214–405`). После этого retirement опять читает/собирает/проверяет весь RES. Цена P1 прямо следует из одновременно живых originalBytes, per-member payload, candidate/stage/readback и больших RGBA-картинок.

**Очистка.** Даже при пустом списке removal prepare вызывает `buildTerrainArchiveWithout`, тот создаёт полный clean RES и full reopen с проверкой каждого сохранённого member (`terrain_atlas_compact.cpp:211–220`, `:385–387`). В commit с пустым списком уже есть early return (`:392`), но он наступает после дорогого preview. Поэтому10,46с и3,16ГиБ получены при реальном нулевом результате.

## 8. Результат и границы

Аудит209 выполнен без исправлений/версии/коммита. Описаны источники, режимы кисти, маски/пиксели генерации, оба вида упаковки, формат ссылок, namespace, сохранность и обслуживающие команды. Текущие42 карты прошли адресную проверку лимита страниц и активного overlay; старое нарушение разрастания не воспроизведено как действующее поведение209. Найдены подтверждённые проблемы затрат/идентичности и отдельно обозначенный риск точности визуальных стыков.

Остаются **не выполненные в этом read-only аудите**: игровая приёмка всех42 карт на аддоне; визуальный двухкарточный сценарий общей кисти/Resolve; измерение полной сцены с MOB и реально представленным кадром; статистика многих cold/warm прогонов; новое исследование оригинального game.exe с точной source/binary identity. Они не заменены вымышленным PASS. Для объяснения оставшихся проблем достаточно текущих исходников, сохранённых данных и приведённых production209 замеров; бесконечные повторы тех же успешных проверок не выполнялись.
